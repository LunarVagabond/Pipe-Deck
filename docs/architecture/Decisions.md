# Product Decisions

## Purpose

Centralized record of accepted product and architecture decisions for Pipe Deck.

## Decision Log

### PD-001 Default Landing View

- Status: Accepted
- Decision: Dashboard is the default first-launch landing page.
- Rationale: Fast orientation around current audio state improves confidence for new users.

### PD-002 Routing Apply Model

- Status: Accepted
- Decision: Routing edits apply immediately by default.
- Constraint: Undo/rollback is required for all routing edits.
- Rationale: Immediate feedback reduces friction and keeps workflows fast.

### PD-003 Profile Storage Model

- Status: Accepted
- Decision: Profiles are stored as separate YAML files by default.
- Constraint: Main config may maintain a lightweight profile index and active profile pointer.
- Rationale: Better portability, backup, and sharing behavior for user setups.

### PD-004 Plugin Runtime Isolation

- Status: Accepted
- Decision: Plugins run in isolated subprocesses by default.
- Constraints:
  - Capabilities are explicit and denied by default until approved.
  - Plugin failures must not crash or block core routing operations.
- Rationale: Safety and fault isolation are mandatory for extension support.

### PD-005 Rule Engine Precedence and Debug Minimum

- Status: Accepted
- Decisions:
  - Global deterministic conflict policy in MVP.
  - Manual user overrides take precedence for the active session.
  - Minimum debug detail includes matched rule ID, match reason, chosen action, and fallback behavior.
- Rationale: Predictable outcomes and explainability are core product requirements.

### PD-006 Daemon Requirement Boundary

- Status: Accepted (implemented Phase 4)
- Decision: Daemon remains optional until persistence and restore workflows require background ownership.
- Phase 4 implementation: `pipe-deck-daemon` binary, user systemd unit, Settings UI toggle; disabled by default.
- Rationale: Avoid early operational complexity while preserving future extensibility.

### PD-007 Automatic Mapping Rollout Policy

- Status: Accepted
- Decisions:
  - Initial automatic mapping operates in suggest-first mode.
  - Auto-apply requires confidence and safety checks.
  - Disconnect handling uses grace window followed by last known-good fallback.
- Rationale: Automation should reduce effort without hidden or unsafe behavior.

### PD-008 Diagnostics Direction

- Status: Accepted
- Decision: Diagnostics prioritize local explainability and troubleshooting over mandatory telemetry.
- Rationale: Transparency and user trust are more important than early telemetry breadth.

### PD-009 Phase 2 Persistence Model

- Status: Accepted
- Decision: File-first YAML for config and profiles in Phase 2; no SQLite or database layer.
- Constraints:
  - Main config (`config.yaml`) holds preferences, active profile pointer, and profile index.
  - Profiles stored as separate YAML files under `profiles/`.
  - Export/import via file copy or simple archive.
  - SQLite may be introduced later only if indexing, concurrent writes, or daemon reconciliation justify it; YAML remains the portable contract.
- Rationale: Simpler to implement, debug, and share; matches PD-003; sufficient for Phase 2 complexity.

### PD-010 Frontend Styling Model

- Status: Accepted
- Decision: Frontend styles use SCSS partials under `src/styles/`; Vue components must not contain `<style>` blocks.
- Constraints:
  - `src/styles/main.scss` is the single entry imported by `src/main.ts`.
  - View/component styles namespace under a root class (for example `.dashboard`, `.routing-matrix`).
  - Shared theme tokens live in `src/styles/_variables.scss`.
- Rationale: Keeps presentation separate from component logic, makes styles easier to scan and reuse, and avoids scattered scoped blocks.

### PD-011 Lightweight Route Persistence (Phase 2+)

- Status: Accepted (updated Phase 3)
- Decision: Last-chosen routes from the dashboard matrix are saved in `config.yaml` under `routing_rules` and re-applied on graph refresh. Authored `rules[]` (Phase 3) take precedence by priority when both match.
- Constraints:
  - Stream rules key on composite identity (`app_name` + optional `executable` + optional `media_name`); device rules key on virtual sink `system_name`.
  - Authored rules are managed in the Rules view; dashboard explainability shows why each stream routed.
  - Full rule engine (priority, explainability, simulation) is implemented per `Rule_Engine_Spec.md`.
- Rationale: Users need routes to stick when ephemeral streams disappear without learning a separate rules vocabulary, while power users can author explicit policies that override implicit dashboard saves.

### PD-012 Phase 4 Restore Model

- Status: Accepted
- Decision: Virtual device definitions persist in `config.yaml` (`virtual_devices[]`); restore runs on app open by default and optionally at login via daemon.
- Constraints:
  - GUI and daemon share `restore.rs` and the same YAML contract.
  - Daemon safe mode: corrupt or missing config logs status and exits without creating devices.
  - Dashboard-saved routes display as **Manual route** in explainability; authored rules show rule name.
- Rationale: Survive reboots without forcing always-on services; keep automation labels user-readable.

### PD-014 Plugin API Transport

- Status: Accepted (Phase 5)
- Decision: Plugin host communicates via JSON-RPC 2.0 over stdin/stdout with newline-delimited messages.
- Constraints:
  - Request timeout 5 seconds; hung plugins are killed without blocking core routing.
  - `api_version: 1` in manifest must match host support.
- Rationale: Simple, language-agnostic, debuggable transport for subprocess isolation.

### PD-015 First-Party Effects

- Status: Accepted (Phase 5)
- Decision: Audio effects (EQ, compressor) ship as a first-party bundled plugin using PipeWire `filter-chain`; no EasyEffects dependency.
- Constraints:
  - Effects apply only to Pipe Deck-owned virtual devices (`pipe-deck-*`) in v1.
  - Plugin ships enabled by default; maintained in-tree.
- Rationale: Pipe Deck owns the audio stack; effects are core product value, not an external tool integration.

### PD-016 First-Party Audio Ownership

- Status: Accepted (Phase 5)
- Decision: Pipe Deck owns routing, effects, and virtual devices; external audio tool integrations (EasyEffects, OBS) are out of product scope.
- Constraints:
  - Community connector plugins may exist post-Phase 5 but never replace first-party paths.
  - Multi-output routing is a core engine feature (fan-out virtual sink + `pw-link`).
- Rationale: Pipe Deck is the Linux Audio Control Center, not a launcher for other audio tools.

### PD-017 Live Effects Safety Contract

- Status: Accepted (Phase 7)
- Context: an early attempt at live effects processing wrote an unvalidated
  `pipewire.conf.d` drop-in containing an FFmpeg `acompressor` filter-chain
  node, then automatically restarted PipeWire to load it — this crashed the
  user's PipeWire session (issue #64). Earlier approaches were also tried and
  rejected: `pactl load-module module-filter-chain` (not available via the
  Pulse compat layer) and `pw-cli load-module` (loads into `pw-cli`'s own
  local instance only, never `pipewire-0`).
- Decision: live effects processing is re-enabled only under a "two-speed"
  model with a hard safety contract:
  1. Never restart PipeWire without an explicit, user-confirmed Apply action.
  2. Never write a filter-chain config drop-in without passing preflight
     validation first (`pipewire::fx_validate::preflight`).
  3. The v1 live filter graph is **builtin-only** — no FFmpeg nodes, no
     arbitrary third-party plugins (`fx_validate::render_conf` is covered by
     a regression test asserting the rendered config never contains
     `ffmpeg`/`acompressor`).
  4. The filter-chain module entry is loaded with `nofail`, and only the
     dedicated `filter-chain.service` is restarted — never the main PipeWire
     graph (`pipewire::pipewire_restart`).
  5. Any failure during Structural Apply rolls back to a plain sink with no
     conf write and routing left untouched (`apply_effect_chain_structural`).
  6. Startup always cleans up legacy `99-pipe-deck-*` drop-ins regardless of
     whether a live chain is later re-applied.
  - **Live params** (slider drags after a chain is live) push straight to the
    running filter-chain node via `pw-cli set-param` — no conf write, no
    restart, so day-to-day adjustment carries none of the restart risk above.
  - **Structural Apply** (the one-time, user-confirmed "Enable/Disable live
    effects" action) is the only path that writes a conf drop-in and restarts
    `filter-chain.service`.
- Rationale: the incident showed that automating a PipeWire restart around an
  unvalidated config is a session-destroying failure mode, not a cosmetic bug.
  Splitting "live params" (safe, frequent, no restart) from "structural apply"
  (rare, explicit, restart-carrying, preflighted, and rollback-safe) preserves
  a responsive slider UX without reintroducing that risk.

### PD-018 Theming Architecture

- Status: Accepted
- Decision: Color schemes are applied at runtime as CSS custom properties written onto the document root, not as build-time SCSS theme files. Custom-scheme YAML merging (partial overrides against a built-in base palette) happens Rust-side; the frontend always receives a fully-resolved 12-color palette (9 surface/text/accent tokens plus `status_success`/`status_warning`/`status_danger`, added after an initial pass shipped with only 9 — status colors turned out to be hardcoded in several places and are just as legitimately themeable, e.g. for colorblind-friendly custom schemes).
- Rationale: the app's SCSS already consumed a single hardcoded `:root` custom-property palette across every view/component, so runtime injection required no per-file rewrites. Doing the merge in Rust keeps the built-in palettes as the single source of truth and means any future plugin-facing theme API (see [Plugin API](../specs/Plugin_API.md)) also only ever sees resolved colors, not partial YAML.
- Constraint: the static `_variables.scss` `:root` block is kept as-is as the pre-JS/failure-mode fallback (Midnight Deck).
- Constraint: the native OS window title bar/decorations (minimize/maximize/close) are outside CSS's reach entirely — Pipe Deck uses native decorations, not a custom-drawn title bar. Best-effort theming is done via Tauri's cross-platform `Window.setTheme('light'|'dark')`, called whenever the resolved scheme's `kind` changes; this is wrapped defensively (try/catch, dynamic import) since it only makes sense on desktop platforms with a themeable native title bar. No explicit OS branching was added — `setTheme` is already a cross-platform Tauri abstraction (Windows/macOS/Linux), and on a future non-desktop port the call simply no-ops/throws-and-is-caught rather than needing a dedicated code path.

### PD-019 Cross-Platform Scope, Audio Backends, and Feature Parity

- Status: Accepted
- Context: Pipe Deck's core engine, restore workflows, and effects are built directly around Linux PipeWire (`pw-dump`, `pactl`, `pw-link`, systemd user restore). The Stretch — Cross-Platform Port milestone (#67-#75) is a long-term personal goal to bring Pipe Deck to macOS and Windows; before investing in backend or UI work for those platforms, this ADR fixes the target APIs, what "parity" means per platform, and what is explicitly out of scope.
- Decision:
  - **Linux remains the primary, fully-supported platform.** Nothing in this ADR changes near-term Linux behavior or priorities; the stretch milestone has no numbered release commitment.
  - **macOS target:** Core Audio for device discovery, routing, and mixer control. Virtual devices (Pipe Deck-owned sinks/sources equivalent to today's `pactl` null sinks) require a third-party virtual audio driver (e.g. BlackHole or an equivalent aggregate-device-based approach) — Pipe Deck does not bundle or install a kernel extension/driver itself; device creation is a discovery + configuration problem against a driver the user installs, not code Pipe Deck ships.
  - **Windows target:** WASAPI for discovery, routing, and mixer control. Virtual devices similarly require a user-installed virtual cable driver; Pipe Deck configures and routes to it rather than shipping a driver.
  - **Backend abstraction:** the pluggable `AudioBackend` boundary proposed in #68 is the mechanism for all of the above — one trait owning graph fetch/subscribe, link/create/remove, volume/mute, and virtual device lifecycle, with today's PipeWire code moving behind a `LinuxPipeWireBackend` implementation and the mock backend remaining available for tests on any host OS. Backend selection is compile-time (`#[cfg(target_os)]`) or an explicit factory — never a runtime plugin.
  - **Feature parity matrix** — what ships per platform in a v1 port:

    | Capability | Linux | macOS | Windows |
    |---|---|---|---|
    | Device/stream discovery | Full | Full | Full |
    | Per-app routing | Full | Full | Full |
    | Virtual devices | Full (native, `pactl` modules) | Requires user-installed driver | Requires user-installed driver |
    | Mixer (volume/mute) | Full | Full | Full |
    | Rules engine | Full | Full | Full |
    | Background restore (daemon/login) | Full (systemd user service) | Deferred — needs LaunchAgent equivalent (#71) | Deferred — needs Task Scheduler/service equivalent (#71) |
    | Tray quick controls | Full | Deferred (#71 scope) | Deferred (#71 scope) |
    | First-party effects (filter-chain/LADSPA-based) | Full | Deferred — needs a portable effects pipeline (#74) | Deferred — needs a portable effects pipeline (#74) |
    | Plugin host (JSON-RPC subprocess) | Full | Full (transport is OS-agnostic) | Full (transport is OS-agnostic) |
    | Rule matchers keyed on process/window identity | Full (X11/Wayland) | Needs platform-specific identity source (#75) | Needs platform-specific identity source (#75) |

  - **Non-goals (explicitly out of scope for the stretch port):**
    - Bundling, signing, or installing kernel-level audio drivers on any platform — Pipe Deck configures against user-installed virtual audio drivers, it does not ship them.
    - Real-time / pro-audio latency guarantees beyond what each platform's standard API (Core Audio, WASAPI) provides out of the box.
    - Mobile platforms (iOS, Android) or sandboxed store distribution (Mac App Store, Microsoft Store) parity — packaging targets are native installers only (#73).
    - Feature parity on day one of a port landing — the matrix above is the target end state; individual capabilities land as their own tracked issues (#69-#75) and may ship Linux-only for a period.
  - **Open questions (deferred, not blocking #68):**
    - Virtual driver installation/consent UX on macOS/Windows (guiding the user through installing BlackHole/a virtual cable) — owner unassigned, tracked under #72.
    - Portable effects pipeline design once off PipeWire `filter-chain`/LADSPA — owner unassigned, tracked under #74.
    - Codesigning/notarization workflow for macOS and Windows release artifacts — owner unassigned, tracked under #73.
- Rationale: fixing target APIs and a parity matrix up front prevents the backend abstraction in #68 from being designed against an unstated or shifting definition of "cross-platform," and makes explicit that virtual devices — Pipe Deck's most PipeWire-native capability — are the highest-risk parity gap on both other platforms since neither macOS nor Windows exposes an equivalent to `pactl` null-sink modules without a third-party driver.

### PD-020 Node-Scoped Effects, Not Connection-Scoped

- Status: Accepted
- Context: Issue #105 first shipped a per-*connection* volume control: a `pipe-deck-connfeed-*` feed sink inserted between one specific source→target pair, giving that one connection an independent gain distinct from the source's own volume. It broke routing in production. Device-sourced connections never tore down the original direct link, so the target received the signal twice (doubled/echoed audio) and the new slider audibly did nothing. Stream-sourced connections rerouted correctly at the pactl level, but `stream_match.rs`/`graph_enrich.rs` only recognized the older `pipe-deck-feed-` naming, not the new `pipe-deck-connfeed-` naming, so the stream's edge silently vanished from the graph on every refresh. Neither failure raised an error — both were pure topology/graph-model gaps. Replaced same-day with a node-scoped model (this ADR).
- Decision:
  - **Effects attach to a node, never to a specific connection/edge.** A node's effect chain shapes its own output once, before that output is piped anywhere downstream — it does not vary by which target the node happens to be routed to. (Concretely: if a source feeds two different outputs, it has one volume, not two independent ones — this is a deliberate simplification from the original per-connection ask.)
  - **Volume is a permanent, pinned, always-present first row** on every effects-capable node — not something you add. It represents the node's real, final output gain (`set_device_volume`/`set_stream_volume`, the same mechanism that already existed pre-#105 — no new PipeWire object, no topology change, so this class of bug cannot recur for Volume). It never moves from the top of the list, since it's the final gain stage, not an interchangeable link in a processing chain.
  - **Future effect kinds attach below Volume**, added via a per-node context menu ("Add effect") and drag-reorderable **among themselves** (order matters once more than one stage exists — e.g. one stage's distortion feeding into the next) — but never reordered above Volume.
  - **Scope: audio source streams and Pipe Deck's own virtual devices** (mixer/mic/virtual outputs) are effects-capable. Physical hardware devices (real mics, real speakers/headphones) are explicitly out — they keep only their pre-existing plain volume control, no effects-list framing, since Pipe Deck doesn't own or control their processing path the way it does its own virtual sinks. This may be revisited later, but is not assumed by default.
  - **Any future effect's DSP mechanism must not insert a new PipeWire object into the middle of an existing connection** — that's the specific mistake this ADR reverses. The existing per-device filter-chain swap-by-identity mechanism (PD/issue #15: unload the device's own null-sink module, replace it with a filter-chain node under the same name, relink downstream once) is the template for extending real DSP (EQ, compression, etc.) to Pipe Deck's own virtual devices. Physical devices and app streams have no equivalent swappable module — extending real DSP to them needs a different, not-yet-designed mechanism, and is explicitly flagged as harder future work, not something to improvise via another connection-scoped feed sink.
- Rationale: the incident showed that "independent gain per connection" and "no new routable PipeWire object" are in tension for any source that fans out to multiple targets — the only way to keep both was to keep inserting per-pair objects into live topology, which is exactly the failure mode encountered. Scoping effects to the node instead sacrifices per-target independence (same source, same level everywhere it's routed) in exchange for correctness by construction: a node's own volume/effects chain never has to touch or reason about topology at all.

### PD-021 Plugin `effects.manage` Enforcement: Queued Requests, Not Direct PipeWire Access

- Status: Accepted
- Context: `effects.manage` (`docs/specs/Plugin_API.md`) was declarable and grantable in Settings since v1 but had no host-side handler — granting or revoking it had no runtime effect (#120). Closing that gap means letting a plugin actually request an effects change, but the plugin host (`src-tauri/src/plugins/`) has no reference to `CoreEngine`/`AudioBackend` at all — by design (issue #68's boundary: engine/core code never lets outside callers reach `backend::linux` directly), and giving it one just to satisfy this one capability would be a much bigger structural change than the gap warrants.
- Decision:
  - `effects.manage` is enforced via a **queued-request model**, not a direct call path. A plugin sends an `effects.apply` notification (`{device_id, config}`); `PluginProcess::handle_line` (gated by the capability, mirroring `routing.suggest`) stores it in a small per-process bounded queue — it does not touch PipeWire and has no engine reference.
  - `CoreEngine::apply_queued_plugin_effect_requests` (called once per `refresh_graph`/`apply_graph_update` tick, right after `push_graph`) drains that queue and applies each request through the **existing, already-safety-checked** `set_device_effects` engine method — the same path the first-party effects UI already uses. No new PipeWire-touching code was written for this; the plugin path reuses `set_device_effects`'s built-in `pipe-deck-*`-only device guard verbatim.
  - Every applied (or rejected) request is audit-logged (`~/.local/state/pipe-deck/plugin-audit.jsonl`) with the requesting `plugin_id`.
  - This keeps the plugin host provably incapable of reaching `AudioBackend`/PipeWire directly — a plugin can only ever ask, on a tick-delayed basis, for something the host was already willing to do for its own first-party UI.
- Rationale: reusing `set_device_effects` instead of building a plugin-specific effects-apply path avoids a second, divergent safety implementation (the exact risk PD-015/PD-017 already guard against for first-party effects); the queue keeps the plugin host itself free of any `CoreEngine`/backend dependency, preserving the issue #68 boundary this repo is deliberately strict about.

### PD-022 Plugin Crash-Loop Backoff

- Status: Accepted
- Context: `PluginManager::start_plugin` (`src-tauri/src/plugins/registry.rs`) had no memory of prior failures — every call (from `set_enabled`, `rescan`, or app-startup `start_enabled`) attempted a fresh subprocess spawn regardless of how many times that plugin had just crashed on `initialize` (#102). There's no periodic auto-restart timer in this codebase, so an unattended tight loop wasn't reachable yet, but repeated manual rescans/toggles against a broken plugin had no backoff, and there was no guard rail to make a future auto-restart tick safe.
- Decision:
  - `PluginManager` tracks a per-plugin `RestartState` (consecutive failure count, next-retry timestamp, disabled reason), consulted and updated inside `start_plugin`.
  - A failed `initialize` sets an exponential backoff window (`250ms * 2^(failures-1)`, capped at 5s) before the plugin can be attempted again; a `start_plugin` call inside that window is skipped without touching `last_error` (so the UI keeps showing the real crash reason, not a transient backoff message).
  - After `MAX_CONSECUTIVE_FAILURES` (3) consecutive crashes, the plugin gets a `disabled_reason` and is refused further automatic starts until a user explicitly re-enables it — `set_enabled(id, true)` clears the restart state first, since a deliberate manual retry should never be blocked by leftover crash-loop bookkeeping.
  - `disabled_reason` rides on the existing `PluginStatus`/`list_plugins` payload (no new Tauri command), surfaced in Settings → Plugins next to the existing `last_error` display.
  - Resource ceilings (cgroups CPU/memory limits) proposed in the same issue are out of scope for this decision — this covers crash-loop backoff only.
- Rationale: keeping the backoff state entirely inside `PluginManager` (not a new timer/thread) matches the fact that plugin (re)starts are already only ever triggered by explicit calls (enable toggle, rescan, startup) — there was no need to invent a health-check loop just to make those explicit call sites safe against being hammered against a broken plugin.

### PD-023 Frontend Graph-Update Throttling: Debounce+MaxWait, Not rAF

- Status: Accepted
- Context: the backend already coalesces PipeWire monitor events before emitting `graph-updated` (`MONITOR_DEBOUNCE`/`MAX_COALESCE_WINDOW` in `backend/linux/live.rs`, ~2-5Hz worst case), but the frontend (`useRuntimeGraph` in `src/stores/runtimeGraph.ts`) applied every event unconditionally with a full reactive replacement, triggering a `RoutingGraph.vue` rebuild on each one (#57). There was no client-side rate bound at all.
- Decision:
  - Inbound `graph-updated` events are run through a trailing-edge debounce with a max-wait ceiling (`src/composables/useThrottledGraphUpdates.ts`, `createTrailingDebouncer`) before being written to reactive state: 100ms wait, 150ms max-wait.
  - This mechanism — not a plain debounce, not `requestAnimationFrame` batching — is the standing policy for any future case of bounding a bursty *inbound* event stream in this codebase. A plain debounce risks starving updates indefinitely under sustained churn (each event resets the timer). rAF-batching ties the update rate to paint cadence rather than a fixed budget, and isn't deterministically unit-testable without polyfilling `requestAnimationFrame`; debounce+maxWait is tested with fake timers (`useThrottledGraphUpdates.spec.ts`).
  - This is distinct from the existing *outbound* debounce pattern (`useMixerControls.ts`'s `scheduleChannelVolume`, a plain 120ms debounce for user-initiated volume sends) — outbound sends carry only the latest pending value and aren't at risk of sustained-churn starvation the way a live inbound event stream is, so they don't need a max-wait cap.
  - The explicit "Refresh" pull (`useRuntimeGraph().refresh()`, backed by a direct `get_runtime_graph` invoke) is not debounced — it's a one-shot user action, not part of the churn problem this addresses.
- Rationale: keeps worst-case propagation from a live PipeWire change to the routing/mixer UI comfortably inside the "reflects within 500ms of a user action" budget while bounding the Vue Flow rebuild rate under sustained churn, without coupling the fix to browser paint timing.

### PD-024 Effects on Virtual Input Devices, Not Physical Hardware

- Status: Accepted
- Context: Effects v0 (#15) only applies to `DeviceKind::Virtual && DeviceDirection::Output` devices — there was no way to attach a live effect chain to a virtual input (mic) device, which blocks any voice-changer-style workflow (physical mic → processed virtual mic → apps). Issue #19 asked to attach effect chains directly to physical sinks and capture inputs, but PD-020 deliberately scoped effects to Pipe Deck's own virtual devices only, excluding physical hardware by design — Pipe Deck doesn't own or control a real device's processing path the way it does its own virtual sinks, and that exclusion was a hard-won lesson from the #105 incident, not an oversight to casually reopen (#139).
- Decision:
  - Effects extend to virtual **input** devices using the same node-scoped, swap-by-identity mechanism PD-020 already established for virtual outputs — a second, capture-direction `module-filter-chain` conf template (`media.class = Audio/Source/Virtual` on the exposed side, vs. the existing playback template's `Audio/Sink`), with the module-unload/reload and rollback paths made direction-aware (calling `pactl::create_virtual_source` rather than the output-flavored `create_null_sink` when reverting an input device).
  - PD-020's exclusion of physical hardware is **not reopened**. A physical device (e.g. a real mic) that needs processing must be wrapped by a virtual device first — routed into a virtual input via the existing `mix_sources`/`virtual_mic_mix.rs` mechanism — and the effect chain attaches to that virtual wrapper, never to the hardware device itself. This is the existing product pattern for virtual devices generally, not a new hardware-facing mechanism.
  - Issue #19 is superseded by this decision for capture inputs specifically: "attach chains to physical... capture inputs" is satisfied via wrap-with-virtual-device rather than a direct-to-hardware mechanism.
- Rationale: reusing the same swap-by-identity template for both directions keeps this within one well-understood, already safety-hardened mechanism (PD-017's two-speed live-effects contract) rather than inventing a second one; keeping physical hardware permanently out of scope preserves the exact guarantee PD-020 was written to establish after #105, while still giving users a working path to "effects on my real mic" through the virtual-device layer Pipe Deck already fully owns.

### PD-025 Effect-Add Is the Explicit Action; No Separate Confirm Dialog

- Status: Accepted
- Context: PD-017's live-effects safety contract requires "never restart PipeWire without an explicit, user-confirmed Apply action" — implemented in `Effects.vue` as a distinct "Enable live effects" button behind a confirm dialog, separate from adjusting any slider. Product feedback on the node-scoped effects UI (#139): this extra step is friction with no real safety benefit once effects are attached directly to a node via an explicit "+ Effect" menu action — the add-effect click is already deliberate and infrequent, not something that happens accidentally per-slider-tick.
- Decision:
  - The explicit, user-confirmed action PD-017 requires is now the deliberate act of adding, removing, or reordering an effect stage via the UI (Routing graph context menu, Mixer disclosure panel, or the `Effects.vue` page) — not a separate confirmation dialog afterward. `add_effect_stage`/`remove_effect_stage`/`reorder_effect_stages` (`core/engine/effects_ops.rs`) call straight through to the existing `apply_effect_chain_structural`/`remove_effect_chain_structural` primitives with no intermediate "enable" step.
  - A one-time, non-blocking toast (not a click-through gate) informs the user the first time in a session that adding an effect briefly restarts Pipe Deck's effects daemon — informational, not a confirmation the user must act on.
  - PD-17 bullets 2–6 (preflight validation before any conf write, builtin-only v1 scope, `nofail` + dedicated-service-only restart, rollback-to-plain-sink on any failure, startup cleanup of legacy drop-ins) are all unchanged — only the UX gate in front of Structural Apply changes, not the safety mechanics behind it.
  - The restart mechanism itself (conf.d + `systemctl restart filter-chain.service`) is unchanged in this decision — eliminating the restart entirely is tracked separately (#141: native zero-restart apply via a long-running process linking `libpipewire` directly), a larger, distinct initiative not folded into this one.
- Rationale: PD-017's actual concern (see the #64 incident it was written after) was an unvalidated config silently crashing the session via an automated restart with no human decision point at all — a deliberate "+ Effect" click already is that decision point, preflighted and rollback-safe. Requiring a second, separate confirmation after the user has already chosen to add an effect protects against nothing additional; it only adds friction, which is precisely the feedback that prompted this change.

### PD-026 Virtual Outputs Chain Into Virtual Outputs; Framed as Busses, Not Renamed as a Data Type

- Status: Accepted
- Context: #143 reported that a virtual output could not be routed as a source into another virtual output — chaining a submix into a master mix was rejected — caused by `targetsForVirtualSink` (`src/utils/routingLayout.ts`) hardcoding valid fan-out targets to only physical outputs and virtual inputs, with no backend-side restriction (`split_sink::apply_sink_targets`/`validate_fan_out_target` already permitted it). #144, filed alongside it, asked a broader question first: should "virtual input/output" be reframed as an audio-bus mental model, and is the routing gap a wording problem or a real feature gap? Investigation confirmed both: an unintentional UI-only restriction (no ADR ever justified excluding this), and a genuine wording mismatch — docs and UI copy described virtual devices as "sink/source types you create" rather than the bus-like grouping/processing/chaining behavior users actually want.
- Decision:
  - `targetsForVirtualSink` and `connectionRules.ts`'s `isMicMixCandidate` now allow virtual-output → virtual-output routing as a plain route (`device_route`/`device_targets`), distinct from the mic-mix merge path, which `isMicMixCandidate` now scopes strictly to `target.direction === "input"` instead of the previous overly-broad `!== "duplex"`.
  - `split_sink::apply_sink_targets` gained a cycle guard (`would_create_cycle`) — sink-to-sink chaining introduces a new A → B → A risk that couldn't exist while virtual outputs were leaves; a cycle is rejected with an explicit error rather than silently applied.
  - UI copy and `docs/specs/UI_Spec.md` (new "Virtual Devices as Busses" section) now describe virtual outputs as busses — group, process, chain onward — while virtual inputs remain intentionally merge-only leaves (a virtual mic is consumed by apps, not chained further). `docs/specs/Audio_Terminology.md`'s existing "Bus"/"Submix" glossary entries already matched this framing; only the "Virtual device" entry needed a cross-reference.
  - `DeviceKind`/`DeviceDirection` and the underlying `module-null-sink` primitive are **not renamed or restructured** — this is a UI mental-model and routing-permission change, not a data-model migration. Renaming the enums/commands themselves was considered out of scope: it would touch every `Device`/`RuntimeGraph` call site (Rust and TS) for no functional gain over the copy/routing changes made here.
- Rationale: the routing restriction had no design justification and directly blocked the "submix feeding a master mix" workflow #143/#144 both described as expected; fixing it is a narrow, low-risk change once confirmed backend-safe. Reframing the copy toward bus language costs little (docs + a handful of UI strings) and resolves the terminology confusion #144 raised, without taking on the much larger, higher-risk cost of an actual `DeviceKind`/`DeviceDirection` rename across the Rust/TS boundary — that remains a candidate for a future, separately-scoped decision if the bus framing proves insufficient on its own.

### PD-027 Filter-Chain Native-Hosting Spike: Feasible, Bigger Than Assumed

- Status: Accepted (research spike concluded; no production change)
- Context: #141 proposed eliminating the conf.d + `systemctl restart filter-chain.service` flow by linking `libpipewire` natively (`pipewire-rs`) from a long-running process, calling `pw_context_load_module`/equivalent directly instead of writing a config file and restarting a whole service. PD-017 had already found that `pactl load-module module-filter-chain` isn't exposed via the Pulse compat layer, and that `pw-cli load-module` only loads into `pw-cli`'s own throwaway local context — never the running `pipewire-0` session — but that finding used a short-lived CLI invocation, not a long-running process, so #141 required a hands-on spike before committing to the approach.
- Decision: a throwaway example binary, `src-tauri/examples/filter_chain_spike.rs` (built only behind the new `spike` Cargo feature — `cargo run --example filter_chain_spike --features spike` — never part of `cargo build`/`cargo test`/`cargo check` by default, since it pulls in `pipewire-rs`/`libpipewire-0.3` dev headers most contributors' environments don't have), was written and run against a real PipeWire 1.5.85 session. Findings:
  - **It works, and differs from PD-017's pw-cli finding.** Pumping the main loop for ~1s after `pw_context_load_module` (rather than exiting immediately, which is what a single `pw-cli` command does) lets the module's async node/port setup finish. The resulting node is a real node in the *actual* running `pipewire.service` graph — confirmed externally via `pactl list short sinks`, `pw-link -o`/`-i`, and `pw-cli ls Node` from a separate process, not just this process's own bookkeeping. 5/5 load cycles succeeded; 0/5 leaked past `pw_impl_module_destroy`.
  - **The processed output side does not auto-link anywhere** — its ports exist but have zero links until something explicitly connects them onward, exactly matching today's `effect_output.*` convention. The existing `pw_link`-based "link the processed output onward" logic in `pipewire/filter_chain.rs` could be reused largely as-is.
  - **A real lifecycle hazard, found the hard way**: calling `pw::deinit()` while any `ContextRc`/`MainLoopRc` (or their underlying raw pointers) are still alive segfaults on shutdown, because their `Drop` impls call into an already-deinitialized library. A production implementation needs one centrally-owned lifecycle for this, not something each call site can get subtly wrong.
  - **Not conclusively answered**: whether repeated load/unload cycles genuinely never leak, or just don't leak measurably over 5 cycles (~560kB RSS growth observed, small but unproven flat) — a longer soak test is flagged as necessary follow-up work, not done here.
  - A design sketch of the `AudioBackend` trait shape this would need — `load_effect_chain`/`unload_effect_chain`/`set_effect_chain_live_params`/`effect_chain_capabilities` — was added to `backend/mod.rs` with default `not implemented` bodies so it requires zero changes to any existing backend. This is documentation of the target shape only; no backend implements it yet, and no call site references it.
- Rationale: the spike's job was to convert #141 from "does this work at all" to "here's what a real implementation has to handle" — it succeeded at that. The mechanism is more promising than PD-017's earlier finding suggested (a long-running process genuinely can attach nodes to the live session, not just its own local context), but a full implementation is a materially larger effort than "swap one API call for another": it needs a correct library-lifetime story inside a long-running GUI process, a leak-soak test longer than 5 cycles, and — per #141's original scoping — closing the `core/engine/effects_ops.rs` → `backend::linux::*` boundary gap at the same time rather than as an afterthought. None of that is done here; this decision records the spike's findings and closes the "is this worth pursuing further" question with a qualified yes, not the trait implementation itself.
- **Addendum (issue #148):** The spike was promoted into production code (`src-tauri/src/pipewire/native_host.rs`), gated behind a new `native-effects` Cargo feature (default off) plus a runtime `PIPE_DECK_NATIVE_EFFECTS=1` toggle, wired through the previously-unused `AudioBackend::load_effect_chain`/`unload_effect_chain`/`effect_chain_capabilities` methods sketched above. Restart-based (`swap_to_effect_chain`) remains the unconditional default. `native_host` is called from the daemon binary (not the GUI binary): `daemon/mod.rs`'s systemd unit changed from `Type=oneshot`+`RemainAfterExit=yes` to `Type=notify`+`Restart=on-failure` (unit-version-marker-gated auto-reinstall for anyone with the old unit already installed) so the daemon stays running instead of restoring-then-exiting, and serves a new GUI↔daemon protocol (`daemon::ipc`: Unix domain socket at `$XDG_RUNTIME_DIR/pipe-deck-native-host.sock`, line-delimited JSON, request/response by numeric id, mirroring `plugins/host.rs`'s existing framing rather than adding an IPC crate). `backend::linux::live::LinuxPipeWireBackend`'s `load_effect_chain`/`unload_effect_chain` call `daemon::ipc::client::NativeHostClient` over that socket; `effect_chain_capabilities()` gates `NativeZeroRestart` on the env var **and** a real live ping, so an unreachable daemon silently falls back to restart-based rather than erroring. This addendum resolves several of the open questions above and leaves others explicitly open:
  - **`pw::deinit()` is deliberately never called** for the life of the daemon process — resolves the segfault hazard above by removing the teardown-ordering race entirely, rather than getting per-call-site ordering right.
  - **"Daemon-owned" now covers both cases.** For users who've already enabled restore-on-login (`background_restore = true`), the persistent systemd daemon hosts native effects directly. For everyone else, the GUI spawns a lightweight, ephemeral instance of the same daemon binary (`daemon::ensure_ephemeral_daemon`, `PIPE_DECK_DAEMON_EPHEMERAL=1`) for the life of the app — ping-first, so the GUI never needs to know or care which one it's actually talking to. Crash-safety for the ephemeral case relies on `libc::prctl(PR_SET_PDEATHSIG, SIGKILL)` set in the child before exec: the kernel guarantees the child dies if the GUI process dies for *any* reason (clean quit, crash, `kill -9`, OOM-kill), not just a clean `app.exit(0)` — no in-app cleanup code can cover a crash, since nothing runs in an already-dead process. `RunEvent::Exit` (newly wired up in `lib.rs`) kills the child explicitly too, as a faster path for the ordinary quit case, but `PR_SET_PDEATHSIG` is what makes the guarantee actually hold. Verified by manually spawning a parent, confirming the child answers pings, then `kill -9`-ing the parent and confirming the child is gone within a second with no orphaned PipeWire module. Deliberately does **not** unload effect chains before the (ephemeral or persistent) daemon dies — the native connection dies with the process either way, and for a user who hasn't opted into persistence, effects not surviving the app closing is the intended behavior, not a gap.
  - **Crash-recovery is implemented**, with one caveat. `daemon::reconcile_live_effects_state` runs before the socket starts accepting requests: it reads persisted effect chains (`ConfigStore::effect_chains()`, keyed by `device_id`) against currently-live virtual devices (`AudioBackend::list_virtual_devices()`), and reloads anything persisted-active-but-not-currently-loaded straight through `native_host` — no `CoreEngine`/`RuntimeGraph` needed, since for a `pipe-deck-*` device `Device.id` is always deterministically `format!("virtual-{}", system_name.trim_start_matches("pipe-deck-"))`. Verified against a real session (`reconcile_live_effects_state_reloads_a_persisted_chain_after_a_simulated_crash`). The caveat: this only restores the audio processing itself, not downstream routing (fan-out targets, mic-mix feeders) for the reloaded node — that's `backend::linux::graph_routing`'s job, which already runs generically on every GUI graph refresh keyed off persisted routing intent, so a reloaded chain's routing comes back on the GUI's next refresh, not instantaneously.
  - **Leak-soak testing is resolved for the day-to-day case.** A new `#[ignore]`d test (`native_host_soak_test_many_load_unload_cycles`) runs 50 load/unload cycles in one process, isolating one-time warmup (RSS jumped ~4.6MB over the first 10 cycles, then flattened) from genuine per-cycle growth (post-warmup growth across the remaining 40 cycles was negative-to-flat in a real run, asserted under a 1MB cap). This is a real automated regression guard, not just a comment — but it's still 50 cycles over a couple of minutes, not the extended production-timescale soak a shipped feature would ideally get before wide rollout.
- **Addendum (issue #205):** A second `#[ignore]`d test, `native_host_soak_test_production_timescale` (`src-tauri/src/daemon/ipc/client.rs`), extends the leak-soak coverage the way the previous addendum flagged as still needed: it drives the real `pipe-deck-daemon` binary as a separate spawned process (not an in-process server thread, so its actual RSS is what gets measured) over `daemon::ipc`, with the cycle count configurable via `PIPE_DECK_SOAK_CYCLES` (default 2000) so the same test serves both a quick check and a long manual run, and adds two signals the 50-cycle test didn't track: open file-descriptor count (`/proc/<pid>/fd` entry count) and orphaned-PipeWire-module count (an external `pactl list short sinks` check, independent of the daemon's own in-memory `is_loaded` bookkeeping, to catch a module that survives `unload_chain` at the PipeWire level even though the daemon thinks it's gone). A real run against a live PipeWire 1.5.85 session completed **1,300 of 2,000 configured cycles cleanly** (stopped intentionally, not from a failure, once the trend was unambiguous) with RSS oscillating flat between ~12.1–12.5MB from cycle 100 onward (no growth trend) and open fd count flat at 15 for the entire run past warmup — zero cycle-level failures (no leaked sink, no stale `is_loaded`, no orphaned module) across all 1,300 cycles. This is a materially longer and more heavily-instrumented run than the original 50-cycle test, though still short of the "many hundreds/thousands of cycles over hours against a long-running daemon" framing #205 opened with — treated as sufficient field confidence to proceed with #149's cutover, with the harness left in place (and its cycle count trivially raisable via the env var) for anyone who wants to run a longer soak later.

### PD-029 Cutover to Native Effects Transport; Restart-Based Mechanism Removed

- Status: Accepted
- Context: #141/#148 (PD-027 and its addendum) landed native, restart-free effects transport behind the `native-effects` Cargo feature and a `PIPE_DECK_NATIVE_EFFECTS=1` runtime toggle, with restart-based (`swap_to_effect_chain` + conf.d + `systemctl restart filter-chain.service`) remaining the unconditional default. #149 made the cutover conditional on the native transport reaching field confidence first — #205 tracked extending leak-soak coverage past the original 50-cycle test to establish that. A real run (issue #205, `native_host_soak_test_production_timescale`) completed 1,300 of 2,000 configured cycles cleanly against the real daemon binary (not an in-process test double) with RSS flat from cycle 100 onward and open-fd count flat at 15 for the whole run — accepted as sufficient field confidence to proceed, short of the full multi-hour production-timescale run #205 originally envisioned (recorded honestly as a PD-027 addendum).
- Decision: native transport is now the **only** effects-hosting mechanism — `pipewire`/`sd-notify`/`libc` are mandatory dependencies (no longer `optional = true`), the `native-effects` Cargo feature and `PIPE_DECK_NATIVE_EFFECTS` env var are gone, and the restart-based mechanism is deleted outright rather than kept as a fallback:
  - `src-tauri/src/pipewire/pipewire_restart.rs` (whole file) and `AudioBackend::swap_to_effect_chain` (trait method + every backend's implementation).
  - The `filter-chain.conf.d` config-writing path and its idempotence-check-by-comparing-conf-contents logic in `core/engine/effects_ops.rs`; `pipewire::filter_chain::conf_path_for_device`/`filter_chain_conf_dir` (as public API — `filter_chain_conf_dir` survives as a private helper purely so one-time startup cleanup can still purge any conf.d fragments left over from before this cutover).
  - The two-poll node/port-reappearance wait (`filter_chain::wait_for_effect_output_ports`/`wait_for_effect_input_ports`) — native transport's own `load_chain` already waits synchronously before returning, so callers never needed a separate post-hoc poll. `wait_for_sink`/`wait_for_source` survive, since `revert_to_plain_device` (recreating a plain pactl sink/source, unrelated to which effects transport was in use) still needs them.
  - `core/engine/effects_ops.rs::relink_other_active_effect_chains` (#210's repair pass for shared-restart collateral damage) and its call sites — a per-device `unload_chain` never touches any other device's node, so there's no collateral damage left to repair. Also closes half of #229 ("removing an effect re-routes the entire graph"): that repair pass only ever covered output-direction devices, so an input-direction (mic) device with its own live chain was never protected before; it needs no protection now, locked in by a new mock-backend regression test.
  - `virtual_devices.rs`'s empty-`module_id`-sentinel backfill hack (was restart-transport-specific bookkeeping).
- New signal needed for a pre-existing requirement: PD-017 §1 ("never silently turn on live processing that wasn't explicitly confirmed") used to be inferred from a restart-based conf.d file surviving on disk across restarts — native transport's liveness is in-memory in the daemon process and doesn't survive that way. Added `EffectChainConfig::live: bool` (persisted, `#[serde(default)]`) as the explicit replacement signal, set by `apply_effect_chain_structural`/`set_effect_chain_live_params` on success, read by `reapply_previously_live_effect_chains` during restore/profile-swap. Pre-existing profiles deserialize `live: false` — an accepted one-time transition (those chains stay persist-only until re-applied once after upgrading) rather than attempting to infer legacy conf-file state.
- New trait method: `AudioBackend::is_effect_chain_loaded(system_name) -> bool`, backed by `daemon::ipc::client::NativeHostClient::is_loaded` (an out-of-process query — correct by construction, since the GUI process asking is never the daemon process actually hosting the chain) rather than the old in-process `pipewire::native_host::is_loaded` call `core/engine/effects_ops.rs` used to make directly, which was a boundary violation (issue #68) and, worse, silently always-false from the GUI binary in practice, since the GUI never itself calls `native_host::load_chain` in-process — that only ever happens daemon-side. `MockAudioBackend` now tracks loaded chains in memory (via real `load_effect_chain`/`unload_effect_chain` calls) instead of pure no-ops, so this precondition guard is exercised for real in mock-mode tests instead of being permanently short-circuited.
- Rationale: the soak evidence is real but not the full multi-hour run originally scoped — recorded transparently rather than overstated, same as PD-027's own honesty about its 50-cycle test. The cutover simplifies effects_ops.rs materially (no more native/restart dual-branch logic) and, as a structural side effect, resolves the primary root cause of #229 without any effects-specific bug fix — only the graph-view race (the other #229 root cause, an independent monitor-thread/command-emit ordering issue) needed an explicit fix, tracked separately.

### PD-030 New-Stream Auto-Apply Gate Keyed on Stream Instance, Not App Identity

- Status: Accepted
- Context: #277 reported a routing rule for Firefox never applying to new Firefox streams — they kept landing on the default device. #116 separately flagged that `StreamIdentityKey` (`app_name`+`executable`+`media_name`) is too coarse to identify a stream *instance* for apps like Firefox, which tears down and recreates its PipeWire node per tab/video while reporting identical identity metadata across tabs. Investigation found both were the same bug: `CoreEngine::apply_rules_for_new_streams` (`core/engine/graph_sync.rs`) gated automatic rule application on a `HashSet<StreamIdentityKey>` "seen" set keyed on the coarse app-level identity, never pruned and never invalidated on rule changes. Once one Firefox stream had ever been observed, that identity was permanently "seen," so every later Firefox stream (a different PipeWire node) was silently skipped for auto-apply — including one that newly matched a rule added after the fact. Manual "Apply rules" masked the bug in testing because it re-evaluates every stream unconditionally, unlike the automatic path.
- Decision: the "have I evaluated this stream instance yet" concern and the "did the user manually override this app's routing" concern were conflated under one `StreamIdentityKey`-keyed set; only the latter actually wants a coarse, cross-instance-stable key (`manual_overrides.rs`, unchanged). The new-stream gate now uses `seen_stream_ids: HashSet<String>`, keyed on `Stream.id` (the actual PipeWire node id) — pruned to the currently-live id set on every refresh (bounds memory; a stream that disappears and later returns with a new id is naturally re-considered), and cleared entirely whenever a rule is created, edited, deleted, or toggled (`CoreEngine::save_rule`/`delete_rule`/`toggle_rule`), so a rule added after a stream already exists takes effect on the very next refresh instead of requiring a manual "Apply rules." `ApplyRulesContext::limit_to_identities` was renamed `limit_to_stream_ids` (`Option<&HashSet<String>>`) to match.
- Rationale: this is a granularity fix, not a new identity concept — the existing coarse `StreamIdentityKey` was already correct for manual-override tracking (a user's "keep Firefox on speakers this session" choice should survive tab churn) and remains untouched; it was simply the wrong key for detecting a genuinely new stream instance, which PipeWire's own node id already identifies unambiguously. Resolves #277 directly and #116 as a side effect for any app with the same coarse-identity/per-instance-churn shape, without introducing per-app special-casing.

### PD-031 Virtual Output Splits Into Bus vs. Terminal Output (Virtual)

- Status: Accepted
- Context: PD-026 fixed virtual-output → virtual-output chaining and reframed virtual outputs as busses in UI copy only, deliberately leaving `DeviceKind`/`DeviceDirection` and the underlying `module-null-sink` primitive untouched — a real data-model split was flagged there as a candidate for a future, separately-scoped decision "if the bus framing proves insufficient on its own." #287 was that follow-up: a single "virtual output" was still being asked to do two different jobs — a processing/fan-out point (a bus) and an actual terminal endpoint — with nothing in the model saying which a given node was; that only became clear from how it happened to be routed at any given moment, not from what kind of node it was.
- Decision: `Device` gains a new `virtual_role: Option<VirtualRole>` field (`Bus | Output`), set only for `kind: Virtual, direction: Output` devices (`None` for physical devices and virtual inputs, which are unaffected by this split):
  - **Bus** keeps every existing virtual-output capability unchanged: fan-in from streams/devices, effects-eligible, can route onward to another Bus, a terminal Output, or a virtual-mic mix.
  - **Output (virtual)** is new and stricter: fan-in only, a true dead end. It cannot route onward to anything (enforced in `backend::linux::split_sink::apply_sink_targets`), cannot host an effect (enforced in `core::engine::effects_ops`'s attach gate), cannot be a mic-mix source (enforced in `core::engine::virtual_ops::set_virtual_mic_mix`), and renders with no output pin in the Routing graph at all (`nodePorts.ts::handlesForDevice`) — mirrored by the same three frontend relationship checks (`isRoutableVirtualOutput`, `isMicMixCandidate`, `isMultiSink`) gating on `virtual_role === "bus"`.
  - No new PipeWire primitive is involved — a Bus is still exactly the same `module-null-sink` a virtual output has always been; `module-null-sink` always exposes a monitor/output port with no argument to suppress it, so "no output pin" is enforced entirely at Pipe Deck's own permission layer (backend rejection plus the frontend never rendering the handle), not by removing the underlying PipeWire port. This also means the split doesn't change how the node is exposed to the rest of the system — see the open item below.
  - Migration: every virtual output persisted before this change defaults to `Bus` (`VirtualDeviceSpec::virtual_role`, `#[serde(default = "default_virtual_role_bus")]`), preserving existing chaining/effects capability with zero behavior change on upgrade. The restrictive Output role is reachable only via a new three-way creation choice — "Add Bus" / "Add Output (virtual)" / "Add Input" (`NewDeviceDialog.vue`, the Routing graph's right-click "Add node" menu) — replacing the earlier two-way choice.
- Open item: this decision does not change what the node looks like to the rest of the system — a Bus is still an ordinary PipeWire `Audio/Sink`, directly selectable as a playback destination by any other app (Discord, a browser, etc.) exactly as any virtual output already was. Making a Bus invisible to other apps' own output pickers (an "internal-only" node) would need a further, separately-scoped change — tracked as issue #288.
- Rationale: splitting "can this be routed onward" from "is this a terminal endpoint" resolves the ambiguity PD-026 left open, using the same node-kind/direction-flag pattern (`multi: bool`) the codebase already had precedent for, rather than a new `DeviceKind` variant that would have forced every `Device { .. }` literal (~40 sites) to reason about a distinction that only ever applies to one existing kind. Keeping the underlying primitive unchanged (still `module-null-sink`) kept this a routing-permission change, not new PipeWire plumbing — cheaper than PD-026 speculated a full split might be.

### PD-032 Dedicated Processing Nodes Supersede Node-Attached Effects

- Status: Proposed
- Context: PD-020 (post-#105) established that effects attach to a node's own identity and never introduce a new routable PipeWire object mid-connection — a deliberate reaction to a per-connection feed sink that broke production two ways: an incompletely torn-down link doubled/echoed audio, and a naming mismatch (`stream_match.rs`/`graph_enrich.rs` only recognizing the older `pipe-deck-feed-` prefix, not the new one) made the graph silently drop a stream's edge. That model held for "one effect chain shaping one existing node's own output." Issue #293 asks for capabilities it cannot express without distortion: an N-in Mixer with independent per-input gain, a 1-in/N-out Fan-out, and a growing family of effect kinds — none of which are "a property of one existing device," they are their own processing stages with their own port topology. Bolting these onto `Device`/`EffectChainConfig` would mean either overloading `Device` with multi-port semantics it was never modeled for, or reintroducing the implicit, UI-only-tracked plumbing `docs/specs/UI_Spec.md`'s "Effects as Attachments" section ("an attachment must never become its own node — if it ever does, that's a bug") was written to forbid. This decision retires that rule rather than violating it.
- Decision:
  - A new first-class graph entity, **`ProcessingNode`**, is introduced in `core/models.rs` — parallel to `Device` and `Stream`, added as `RuntimeGraph.processing_nodes: Vec<ProcessingNode>`, not a property of either existing type. Every Mixer, Fan-out, 5-Band EQ, and stub effect kind is a `ProcessingNodeKind` variant of this one entity (`Mixer { input_gains_percent }`, `FanOut`, `Eq5Band { .. }`, `Stub { stub_kind }`), not a bespoke type per kind.
  - Every `ProcessingNode`'s backing PipeWire object is named under one new prefix, `pipe-deck-proc-{kind}-{id}`, sibling to (not a variant spelling of) the existing `pipe-deck-feed-`/`pipe-deck-split-` prefixes. `pipewire::filter_chain::is_pipe_deck_device` (`starts_with("pipe-deck-") && !starts_with("pipe-deck-feed-") && !starts_with("pipe-deck-split-")`) already includes the new prefix with **no code change** — this is deliberate: the predicate is exclusion-based, so a genuinely new prefix is automatically covered rather than needing to be added to an inclusion list, which is exactly the shape of allowlist that missed `pipe-deck-connfeed-` in #105.
  - The real risk isn't a missed exclusion, it's **wrong-bucket inclusion**, and it lives specifically in the virtual-device *registry* path, not the raw pw-dump scan: `pw_dump::normalize` already skips every `pipe-deck-*`-named node outright (it's rebuilt from persisted/registry state instead, not sniffed from the live node list), so it needs no change. `pactl::list_pipe_deck_modules` (`backend/linux/pactl/virtual.rs`, matches any `sink_name=pipe-deck-*` module arg except `pipe-deck-feed-`) and `VirtualDeviceRegistry::discover_from_pactl` (`backend/linux/virtual_devices.rs`, same exclusion) are what rebuild `graph.devices` for every pipe-deck-owned sink on a live rescan — left unchanged, a `pipe-deck-proc-*` sink would get silently absorbed into the `VirtualDeviceRegistry`/`graph.devices` instead of staying a `processing_nodes` entry, the direct descendant of #105's "enrichment code doesn't recognize the new object" failure, just manifesting as misclassification instead of a dropped edge. Both gain the same `pipe-deck-proc-` exclusion already applied to `pipe-deck-feed-`, so processing nodes never enter `VirtualDeviceRegistry` at all — they get their own separate discovery/listing path (`ProcessingNodeRegistry` or equivalent, owned by the new engine module in §Backend Design) rather than being merged through `merge_virtual_devices`. A new `naming_allowlist_coverage` test (Rust, mirrored in a TS unit test) asserts a synthetic `pipe-deck-proc-mixer-test` name is: (a) recognized as a Pipe Deck object by `filter_chain::is_pipe_deck_device`, and (b) explicitly excluded by `pactl::list_pipe_deck_modules` and `VirtualDeviceRegistry::discover_from_pactl`, the same way `pipe-deck-feed-` already is. CI fails if a new call site is added without updating this table.
  - Creating, replacing, or removing a `ProcessingNode` reuses and generalizes the capture-before-swap + rollback-on-failure pattern already proven in `core/engine/effects_ops.rs::apply_effect_chain_structural`/`downstream_and_upstream_routes`: capture every upstream source link and downstream target link for **all** ports before touching PipeWire, swap/create under a stable identity, relink everything captured, and on any failure fully revert (unload anything partially loaded, restore prior links). This targets #105's incomplete-teardown failure mode directly, generalized from 1 port to N.
  - Removing a node where relinking would be ambiguous (e.g. removing a 3-input Mixer — which upstream source should inherit the downstream target?) is **rejected with a clear error**, never guessed. Only unambiguous 1:1 relink-through is performed automatically.
  - **Why a new routable object doesn't reopen PD-020's actual failure mode**: PD-020's invariant was "no independently-drifting shaping point introduced per-connection" — the rejected mechanism created a *new object per source/target pair*, so one source feeding two targets got two ungoverned gain objects the graph model didn't durably track as related. A `ProcessingNode`'s config lives once, addressed by `(node_id, port_index)`, persisted on the node itself, and does not multiply if its output later fans out further (that's the separate, explicit Fan-out kind, chained visibly rather than synthesized implicitly). The invariant PD-020 actually cared about is preserved; only the stricter, more literal reading ("no new object, period") is relaxed, because #293's scope makes that literal reading untenable.
  - **Mic-mix is retired as a distinct mechanism.** `Device.mix_sources` / `backend/linux/virtual_mic_mix.rs` / `connectionRules.ts`'s `isMicMixCandidate` dashed-edge special case become the Mixer Node's first supported use case. Already-persisted profiles get a one-time load migration: any `Device.mix_sources` with no corresponding Mixer node yet synthesizes one (`input_gains_percent` from each source's `volume_percent`), idempotent, using the same custom-`Deserialize` migration pattern `EffectChainConfig` already uses for legacy flat `eq_*` fields. The legacy `mix_sources` field stays present (`#[serde(default)]`) as a read-only fallback for one release; no code path writes to it after this ships.
  - `docs/specs/UI_Spec.md`'s "Effects as Attachments" section is rewritten to "Processing Nodes," explicitly superseding the never-become-a-node rule, while the PD-025 UX principles that still apply carry over unchanged: reversible add/remove with nothing orphaned, immediate-on-add with no separate confirm step, and plain device/stream Volume stays a pinned property (`set_device_volume`/`set_stream_volume`), never itself a processing node.
  - This decision supersedes **PD-020** and builds on the swap-by-identity/capture-before-swap mechanisms established by **PD-024** (capture-direction effect chains) and generalized by **PD-029** (native-only effects transport — `ProcessingNode` DSP kinds load through the same mandatory `daemon::ipc` → `native_host` path `load_effect_chain` already uses; no new transport is introduced or re-litigated here). It relates to **PD-026** (bus-to-bus chaining/cycle guard in `split_sink.rs`, which Fan-out's backend evaluates reusing) and **PD-031** (`VirtualRole::Bus`/`Output` — a terminal virtual Output stays a dead end and cannot host or be replaced by a processing node, consistent with its existing "cannot route onward" restriction).
- Rationale: PD-020's actual invariant — no independently-drifting shaping point per-connection — is preserved by construction; what's relaxed is PD-020's stricter implementation choice (no new object at all), which #293's multi-port requirements make untenable to keep. Naming-allowlist sprawl and incomplete teardown, the two concrete things that actually broke in #105, are addressed as structural, testable properties (an exclusion-based canonical predicate plus a coverage test spanning every classification call site; one generalized capture-before-swap-with-rollback primitive) rather than informal discipline — the concrete lesson #105 leaves for any future decision that introduces a new routable object.

### PD-033 VirtualRole::Bus Removed; Plain Devices No Longer Route Onward

- Status: Accepted
- Context: PD-031 split virtual outputs into `Bus` (fan-in, effects-eligible, can route onward — including multi-target fan-out) and terminal `Output` (fan-in only, dead end). #293's dedicated processing nodes (PD-032: Mixer, Fan-Out, EQ5Band) now cover everything Bus's "route onward" capability existed for — fan-out to multiple destinations is the Fan-Out node's job, combining sources with independent gain is the Mixer node's job, and effects live on the dedicated EQ node instead of attached to a device. That left Bus doing nothing a dedicated node doesn't already do better, while `Device.virtual_role`'s Bus/Output distinction kept a second, parallel routing-permission system alive alongside the new node-based one — worth removing once confirmed there was nothing else depending on it.
- Decision: `VirtualRole` (and `Device.virtual_role`/`VirtualDeviceSpec.virtual_role`) is deleted outright, not folded into a single remaining variant. Every virtual output device now uniformly behaves the way terminal `Output` already did: fan-in only, no forward routing of any kind, no output pin in the Routing graph (`nodePorts.ts::handlesForDevice`), no device-attached effects. Concretely:
  - `apply_sink_targets`/`fan_out_sink` (`backend/linux/split_sink.rs`) — the mechanism that let a Bus route onward, single-target or multi-target — is deleted. `effective_fan_out_source`/`prune_stale_fan_out_links` are kept; they're general primitives processing-node relinking (`relink_processing_node_port` in `backend/linux/live.rs`) and live-graph sync (`graph_routing.rs::apply_pw_link_device_routes`) still need, independent of Bus.
  - The `DeviceRouteRule` routing-automation rule type (`core/routing_rules.rs`, `core/rules/evaluation.rs`/`matching.rs`/`manual_overrides.rs`) is deleted — it was reachable only via a virtual-Bus-device source, so it became permanently dead code the moment no device can route onward. It was never surfaced in any rule-editor UI (confirmed by grep before deleting).
  - Device-attached effects (`core::engine::effects_ops`) are now virtual-input (mic)-only; a virtual output device can no longer host an effect chain directly at all. The dedicated EQ5Band processing node is the only way to get EQ on an output-side signal going forward.
  - `set_device_route`/`set_device_targets` (Tauri commands, engine methods, and the frontend's `useRoutingActions.ts`/`connectionRules.ts` drag-to-connect path for device-to-device edges) are deleted — a plain virtual device's output handle no longer exists in the graph to drag from in the first place.
  - `enable_stream_mic_passthrough`'s fallback branch (creating a fresh virtual output and routing it onward to a stream's original hardware target when that target isn't already a Pipe Deck device) loses its routing step and now returns an explicit "not supported yet" error instead of silently doing nothing — a proper redesign is tracked separately (issue reference: see the mic-passthrough follow-up ticket filed alongside this decision).
  - Legacy config: `VirtualDeviceSpec`'s removed `virtual_role` field has no migration — a persisted `virtual_role: bus` key from before this change is simply ignored on load (no `deny_unknown_fields`), not translated into anything, since there's nothing left for it to mean.
  - Two capabilities that read like "Bus-gated" but are not tied to Bus specifically were deliberately kept unrestricted: a plain virtual output device can still feed a Mixer node's input (a monitor tap, not "routing onward" — `core::engine::processing_node_ops::connect_processing_node_port` no longer has a role check at all, matching how a physical device already fed a Mixer with no such gate), and live-graph edge rendering (`current_target`/`current_targets`, populated by `graph_routing.rs` purely from live `pw-link` state for display) is untouched — it reflects whatever topology actually exists regardless of how it got there.
- Rationale: removing Bus is a real feature retirement, not a rename — confirmed by tracing every caller of `apply_sink_targets` (`core/routing.rs`, `core/rules/evaluation.rs`, `core/engine/effects_ops.rs`, `core/routing_rules.rs`) before deleting anything, per PD-020/PD-032's standing lesson that touching topology-adjacent code without full call-site tracing is exactly how #105 happened. Dedicated processing nodes are a strictly more capable, more testable replacement for what Bus did (each node kind is independently addressable, independently wired, and — per PD-032 — carries its own capture-before-swap/rollback semantics), so retiring the older, less structured mechanism once its replacement covers the same ground reduces the number of ways the same outcome (routing a signal onward) can be expressed, rather than leaving two parallel systems to keep in sync.

### PD-034 Bare-Hardware-Target Mic Passthrough Auto-Provisions a Fan-Out Node

- Status: Accepted
- Context: PD-033 removed the ad hoc device-to-device Bus routing `enable_stream_mic_passthrough` used to lean on for its one remaining gap — duplicating a stream's audio into a mic when the stream plays directly to a bare hardware sink, with no Pipe Deck-owned monitor in front of it to tap. That case returned an explicit "not supported yet" error, tracked for a proper fix built on the dedicated processing nodes PD-032 introduced rather than reviving Bus.
- Decision: `enable_stream_mic_passthrough` (`core/engine/passthrough_ops.rs`) branches on whether the stream's current target is already a Pipe Deck-owned virtual output:
  - If it is, behavior is unchanged — the existing per-pair mix-source mechanism taps that device's monitor.
  - If it isn't (most commonly a bare hardware sink), a Fan-Out processing node is auto-provisioned instead: one input (the stream itself), two outputs (the stream's original destination, restoring what direct playback did, and the mic). This is exactly what a Fan-Out already exists to do — one source duplicated to N destinations — so no new routing primitive was introduced.
  - The Fan-Out is keyed one-per-app (`"{app_name} Passthrough"`, `slugify`d into the node id), not one-per-stream — re-triggering passthrough for a later stream from the same app reuses the existing node rather than creating a duplicate, and the call is idempotent (re-connecting an already-wired mic leg returns the same "already mixed" message the tap-monitor path already used).
  - Wiring order connects both outputs before the input, since connecting the input is what actually moves the stream's live sink-input onto the Fan-Out's own sink (`relink_processing_node_port`'s non-Mixer input arm) — doing that last keeps the window where the stream is inaudible everywhere as short as possible.
  - A stale Fan-Out input from a since-reloaded stream instance self-heals the same way a Mixer input's stream port does (issue #304, `processing_node_ops::resolve_input_port_peer`) — the identity-based reconciliation added there applies to any processing node's input port, not just Mixer's, since a Fan-Out's single input is persisted through the identical `ProcessingNodePortSpec` shape.
- Constraints: a Fan-Out node has one whole-node volume/mute, not independent per-output gain — muting the passthrough leg this way also mutes the original destination, unlike the tap-monitor path's independent per-pair gain. Accepted as a known limitation of reusing Fan-Out rather than a reason to build a bespoke mechanism; a user who needs independent control here should route the stream through a Pipe Deck virtual output first and use the existing tap-monitor path instead.
- Rationale: reusing Fan-Out rather than reviving Bus keeps exactly one system for "duplicate a signal across destinations," per PD-033's stated goal — the same tradeoff PD-032 already made deliberately for every other post-#293 fan-out need.

### PD-035 Output Groups Are a Gesture-Driven Fan-Out Variant, Not a New Routing Primitive

- Status: Accepted
- Context: Issue #80 asked for a way to treat several existing outputs (hardware or virtual) as one logical routing target — select 2+ outputs already on the canvas, group them, and get one node with a single virtual input that fans out to every member, without losing the ability to route to any individual member directly (the issue's own "doesn't read as two unrelated, disconnected devices" concern). The issue's own body speculated `module-combine-stream` might be needed as a new PipeWire primitive. Investigation found this framing outdated: `ProcessingNodeKind::FanOut` (PD-032/PD-034) already *is* exactly "one non-growable input, N growable outputs," built on a plain `module-null-sink` + `pw-link` fan-out (`backend/linux/graph_routing.rs::apply_pw_link_device_routes`), and PD-033 already made every virtual output's fan-out unconditional (no gated "multi" mode left to route around). `module-combine-stream` is unused anywhere in this codebase and wasn't live-verified via `pactl load-module` in the dev sandbox that informed this decision — left as a possible future latency-compensation enhancement (`combine.latency-compensate`), not day-one scope, consistent with this project's preference for proven builtin mechanisms over speculative new ones (see the LADSPA-vs-builtin-filter-chain reasoning in CLAUDE.md).
- Decision:
  - A new `ProcessingNodeKind::Group`/`ProcessingNodeSpecKind::Group` variant is added, field-for-field identical to `FanOut` (`volume_percent`, `muted`) and sharing its exact PipeWire mechanism (`load_processing_node`'s `FanOut | Group` match arm in `backend/linux/live.rs` creates the same plain `module-null-sink`) and its growable-output rule (`processing_node_port_growable`). Kept as a distinct enum variant rather than reusing `FanOut` outright so the UI identity (icon, right-click entry point) doesn't require reinterpreting an already-shipped node kind, and so it can diverge later (e.g. per-member volume) without a breaking rename.
  - `CoreEngine::create_output_group(label, member_device_ids)` (`core/engine/processing_node_ops.rs`) composes two already-tested primitives — `create_processing_node` then a loop of `connect_processing_node_port` — into one atomic bulk operation: any mid-loop wiring failure tears the freshly-created node back down via `remove_processing_node` before returning the error, so a failed group creation never leaves a half-wired node behind. Requires at least 2 members.
  - `remove_processing_node`'s ambiguous-removal guard (PD-032's "reject rather than guess a many-to-many relink") is narrowed to only gate on a kind's *non-growable* side. A growable side being removed is never actually ambiguous — there's nothing to relink, only disconnect several copies of the same one signal — so a Group/Fan-Out with many members now deletes cleanly in one action instead of requiring every member disconnected by hand first. This is *not* extended to Mixer's growable *input* side: deleting a Mixer actively summing 2+ independent live sources is a materially bigger, more surprising action (each source loses its only route through the node, not just an extra copy), so that side keeps its original strict check.
  - Creation is gesture-driven, not menu-driven: shift-click/marquee-select 2+ existing output-direction device nodes on the canvas, then right-click → "Group Selected Outputs" (a new `RoutingGraphMultiNodeMenuTarget`, `routingGraphContext.ts`). Deliberately *not* the existing "G" keyboard shortcut, which already does something unrelated — a purely cosmetic, client-only bounding-box grouping (`routing-graph/groups.ts`/`RoutingGraphGroupNode.vue`, zero backend effect, predates this decision and is untouched by it).
  - **Revised after initial live testing**: a Group draws *no* graph edges to its members at all — it behaves like a terminal/leaf node on the canvas, the same way a plain hardware output never shows downstream wiring. Real member devices stay exactly where they are and remain fully independently routable elsewhere; grouping a device doesn't claim it exclusively, and — unlike the first cut of this decision — the real member node carries no visual trace of group membership either. Members are shown as an inline name list on the Group node itself instead (`RoutingGraphNodeGroup.vue`), toggled by the same per-node collapse/expand affordance (`composables/groupExpansion.ts`, plain localStorage-backed state, same tier as `groups.ts`); collapsed is the default. Hovering a member row highlights that member's real node elsewhere on the canvas (`setHighlightedNode`/`isNodeHighlighted`, an amber glow distinct from the purple multi-select highlight) instead of a persistent edge, and each row has a remove-from-group button (`disconnect_processing_node_port` on the Group's output side — no new backend command needed).
  - **Second revision, same round of live testing**: a Group node renders *no output pin at all* (`handlesForProcessingNode` in `nodePorts.ts`) — only its single input pin, matching the "terminal output" framing exactly (a plain output device has no output pin either). Members are added via a "+" button in the node's header (next to Delete), opening a picker of every terminal output not already a member (`groupAvailableDevices`, `buildGraph.ts`) and calling the existing `connect_processing_node_port` on selection — no drag-to-connect, no new backend command. Disconnecting a Group's *last* remaining member now removes the group node itself outright (`disconnect_processing_node_port` in `core/engine/processing_node_ops.rs`) — a Group's entire identity is its member set, so zero members means the node is meaningless; this is deliberately *not* extended to Fan-out, where a transient 0-output state may be a legitimate mid-edit step for that more general-purpose node.
- Constraints: same whole-node-only volume/mute as `FanOut` — no independent per-member gain (same accepted limitation PD-034 already documented for Fan-Out). A device can only be a connected peer of one processing node at a time (`connect_processing_node_port`'s existing move-semantics, not new) — adding a device already in Group A to Group B silently detaches it from A first, mirroring how connecting the same stream to a second node's input already abandons the first.
- **Related bug found and fixed during this work, not part of the original design**: `resolve_playback_target_device_id` (`backend/linux/stream_match.rs`) had a branch for Mixer's per-input `pipe-deck-feed-*` indirection but none for a processing node's *own* system_name — which is exactly what Fan-out/Group use, since a stream's sink-input moves directly onto the node's own backing sink for those kinds. A stream routed into a Fan-out/Group looked unrouted (or showed the wrong target) after any refresh that re-derives `current_target` from live pactl state, e.g. an app restart, while the node's own port bookkeeping still correctly reported it connected. Fixed by adding the missing direct-match branch.
- Rationale: builds directly on PD-032/033/034 rather than introducing a new PipeWire primitive — zero new backend risk, minimal new Rust surface (one enum variant, one bulk method composing two already-tested single-port operations, one narrowed removal check), and the frontend's internal-wiring visibility requirement is satisfied by `collectEdges.ts`'s existing generic edge-drawing with zero new code there.

### PD-036 Soundboard Clip Playback Is Fire-and-Forget `pw-cat`, Not a Tracked Object

- Status: Accepted
- Context: The Soundboard epic (#127) needs a backend primitive (#393) to play a short clip's audio into a target device (a virtual input or hardware input passthrough) on demand. Unlike every other `AudioBackend` capability, this isn't a persistent object with lifecycle (create/remove/list) or graph presence (device/stream/processing node) — it's a one-shot action with a start and, eventually, a natural end.
- Decision:
  - `AudioBackend::play_sound(path, target_system_name)` (`backend/mod.rs`) shells out to `pw-cat --playback --target <target_system_name> <path>` (`backend/linux/play_sound.rs`), going through `sysproc::command` like every other external PipeWire/PulseAudio process this codebase spawns, never `std::process::Command` directly (see `sysproc.rs`'s own doc comment for why). `--target` accepts a node name directly, so no `pw-dump` id/serial lookup is needed the way `pw_link.rs`'s port-linking helpers need one.
  - The call is spawned (`Command::spawn`, not `.output()`/`.wait()`) and returns as soon as the process starts, not when playback finishes. No completion signal, progress, or stop handle is returned to the caller — `play_sound` answers "did playback start," nothing more. An interrupt/stop mechanism is deliberately deferred to its own ticket (#399) rather than speculatively built alongside the primitive, consistent with this project's general preference (see CLAUDE.md's task-sizing guidance) for not building for hypothetical needs ahead of a ticket that actually needs them.
  - `target_system_name` is a plain device `system_name`, resolved by the caller (`CoreEngine::play_sound`, `core/engine/soundboard_ops.rs`) from a domain `device_id` against the current graph — the same convention `hold_sink_inputs_for_swap`/`list_mic_feeds` already use for one-off, non-persistent backend calls, rather than the `(graph, id)` pair `route_stream`/`set_device_volume` take for routing/mixer state that needs to write back into the graph itself. `play_sound` never mutates `RuntimeGraph`.
  - File existence is validated synchronously before spawning (`path.is_file()` in `backend/linux/play_sound.rs`) so a bad path fails immediately and legibly, rather than surfacing only as a silent, unobserved `pw-cat` exit some time later — the one piece of synchronous validation that's actually possible without waiting on the spawned process.
- Constraints: no volume, mixing with other simultaneous clips, or effects-chain routing for a playing clip in this first slice — a clip plays at its own recorded level straight into the target device's raw input. Per-sound target-device mapping (#395), UI (#396/#398), and stop/interrupt (#399) are separate, later tickets; this decision covers only the playback primitive itself.
- Rationale: reusing `pw-cat` (already the standard PipeWire CLI playback tool, present on any system with PipeWire installed) over hand-rolling a native `pw_filter` playback client keeps the initial soundboard primitive minimal and consistent with this project's preference for proven builtin tooling over new bespoke transports (the same reasoning CLAUDE.md gives for favoring PipeWire's own filter-chain filters over third-party plugins). Fire-and-forget, no persistent tracked object, matches the actual shape of the problem — a clip trigger is momentary, not a routable graph citizen — and keeps this first ticket's surface area small enough to independently test against both the mock backend and a real PipeWire session before any UI exists to drive it.

- Context: #394 initially shipped a single `Preferences.soundboard_folder: Option<String>` — one folder, one flat clip list. Before that PR merged, user feedback (matching how Soundux organizes clips) asked for multiple named groups — e.g. "SFX", "Music" — each pointing at its own folder, plus a native OS folder picker instead of a raw text path field. Reworked in place rather than shipping the single-folder model and migrating later, since nothing had merged yet.

Tying clip grouping to Soundux's tab metaphor keeps this feature recognizable to users coming from that tool, which was an explicit design goal from the start (see this doc's own #395 delivery note and the epic's original framing).

### PD-038 Soundboard Target/Monitor Playback Destinations Are Per-Tab, Not Per-Clip

- Status: Accepted
- Context: #398 first shipped a per-clip destination model — `SoundboardBoard.clip_configs: HashMap<clip_id, SoundboardClipConfig>`, each clip independently pointing at its own target/monitor device and volume, with a gear-icon-triggered per-tile settings dialog. After review, this was more granularity than actually wanted: every user-facing request for this feature was framed at the tab level ("SFX should go here, Music should go there"), not per individual clip, and the per-clip UI (a modal per tile) was real added complexity for a capability nobody asked for at that grain. Per-*tab* mapping (distinct from a hypothetical future per-clip override) was explicitly named as a possible stretch-goal ticket, not something to build speculatively now.
- Decision:
  - `SoundboardBoard.clip_configs` (and the `SoundboardClipConfig` struct) is removed outright — no migration, since #398 hadn't merged yet. In its place, `SoundboardBoard` gains four flat fields directly: `target_system_name: Option<String>`, `target_volume_percent: u8`, `monitor_system_name: Option<String>`, `monitor_volume_percent: u8` (all `#[serde(default...)]`, volumes defaulting to 100). Every clip listed under a board plays through that board's own destinations — there is no per-clip override anywhere in the data model.
  - `CoreEngine::play_soundboard_clip` reads `board.target_system_name`/`board.monitor_system_name` directly instead of a per-clip lookup; the rest of its shape (re-list the folder, resolve the clip, attempt both configured legs independently, surface any failure without swallowing it, error if neither leg is set) is unchanged from #397/#398's original per-clip version — only *what* it reads from the board changed, not *how* it plays.
  - The Soundboard tab UI drops the per-tile gear icon and settings modal entirely. Two device dropdowns ("Target" / "Monitor") and two volume sliders live in a dedicated row between the tab bar's folder toolbar (Refresh/Change folder/Rename/Delete tab) and the clip grid — visible and editable once per tab, not once per clip. Device selection saves immediately (`@change`); volume sliders update their displayed number continuously (`v-model`) but only persist `on change` (drag-release), not on every intermediate tick, to avoid spamming `save_soundboard_board` calls during a drag.
  - A clip tile is dimmed (`.no-target`) based on the *active board's* destinations, not a per-clip lookup — since destinations are board-wide, either every tile in a tab is playable or none are.
- Rationale: matches the feature's actual usage pattern (a user picks one target and one monitor per soundboard "kit," not per sound effect) with substantially less data model and UI surface than the per-clip version carried — one settings row instead of one modal dialog per tile, four flat fields instead of a per-clip map. Keeps the door open for real per-clip overrides later without having built them before anyone asked.

### PD-039 Soundboard Stop Tracks the `pw-cat` Child Directly; Progress Is a Client-Side Timer, Not a Backend Event

- Status: Accepted
- Context: #399 needed two things: a way to interrupt an in-progress clip, and (added to the same ticket) a Spotify-style progress bar on the playing tile. PD-036 deliberately left `play_sound` fire-and-forget with no handle and no completion signal, so both needed a real design rather than reusing something already in place.
- Decision:
  - `backend/linux/play_sound.rs::play_sound` now returns the spawned `std::process::Child` instead of `()`. `AudioBackend` gains `stop_sound(&self) -> Result<(), BackendError>` with a default no-op body (a backend with nothing tracked has nothing to stop); `LinuxPipeWireBackend` is the only implementation that overrides it, holding `soundboard_playback: Arc<Mutex<Vec<Child>>>`. Every `play_sound` call prunes already-exited children (`try_wait`) before pushing the new one, so the vec holds at most the current clip's legs (target + monitor, #398) — never more, since the UI only ever lets one clip play at a time. `stop_sound` kills and reaps (`wait()`, to avoid a zombie) everything currently tracked. `MockAudioBackend::stop_sound` just increments a call counter for tests to assert against — there's no real process to track in the mock.
  - `core::soundboard::list_sounds` probes each clip's `duration_seconds: Option<f64>` via the `lofty` crate (file header/metadata only, no audio decoding — cheap enough to do for every clip on every listing) rather than adding a `AudioBackend`/`pw-cat` mechanism for it; a probe failure yields `None` rather than failing the whole folder listing, and the frontend falls back to an elapsed-only counter with no fixed end when it's `None`.
  - The progress bar itself is **not** driven by a backend push event. `play_soundboard_clip` still only signals "playback started" (PD-036 is unchanged) — there is no PipeWire-side signal for "this specific `pw-cat` invocation finished" cheap enough to poll or subscribe to from the engine. Instead, `Soundboard.vue` starts a plain `setInterval` timer against `Date.now()` the moment its own `play_soundboard_clip` call is issued, using the clip's probed `duration_seconds` as the target; the tile's progress fill and elapsed time (left, counting up from 0:00) are derived from that local timer; the right-hand number is just the clip's probed `duration_seconds` itself, static for the whole play (not a countdown) — matches the Spotify layout this was modeled on. The timer self-clears once elapsed reaches the known duration. A duration-less clip just shows the elapsed counter with no fill/length. Clicking the (now `⏹`-labeled) playing tile calls the new `stop_soundboard_clip` command and clears the local timer state immediately, best-effort — it doesn't wait for or verify the backend kill actually landed before updating the UI. The client tracks one state entry per active clip when overlap mode is enabled.
- Constraints: playback state is purely client-side interpolation against a probed duration, not a verified backend readout — a `pw-cat` process that stalls or a duration probe that's slightly off from actual playback speed will drift the bar, and a second, independent playback started outside Pipe Deck's knowledge isn't accounted for. Good enough for a "roughly where are we" indicator; not frame-accurate transport sync.
- Rationale: avoids adding an event-emission path (`AppHandle` plumbing through `commands/soundboard.rs`, a background task waiting on the child, a new frontend event listener) to solve a problem a client-side timer already solves adequately for a short sound-effect clip — matches this project's preference for the simplest mechanism that fits the actual shape of the problem (a one-shot, bounded-duration trigger, not a long-running transport needing precise sync) over building infrastructure ahead of a need for it.

### PD-040 Graph Fetch/Subscribe Moves to a Native `pw::registry` Connection, Reusing `pw_dump::normalize` Unchanged

- Status: Accepted
- Context: #8 (epic) proposed migrating `LinuxPipeWireBackend` off `pactl`/`pw-link`/`pw-dump` shellouts onto native `pipewire-rs`, in four sequential sub-issues. #410 is the first — graph fetch/subscribe, deliberately scoped as a spike to validate the pattern before committing to the other three (node lookup, port linking, mixer/virtual-device management). Before this, `fetch_graph()` shelled out to `pw-dump -N` and reparsed JSON on *every* call (including every synchronous Tauri command that touches the graph), and `subscribe()` spawned a thread that either watched `pw-dump -m`'s streaming stdout or fell back to a bare 1-second poll — snapshot-and-diff, not real event delivery. `pipewire/native_host.rs` already proved a continuously-running `pw::thread_loop::ThreadLoopRc` is viable in this codebase (the fix for #303's permanently-suspended-node bug), but only for one-shot bind-use-drop calls against nodes it already had an id for (itself resolved via a `pw-dump` shellout, `pw_cli::find_node_id_by_name`) — it never maintained a continuously-updated object graph, which is exactly #410's job.
- Decision:
  - New module `backend/linux/pw_registry.rs`: `NativeGraphWatcher::start()` sets up the same thread-loop/context/core/registry lifecycle `native_host.rs` uses, then registers a registry `global`/`global_remove` listener whose closures do nothing but translate each `Node`/`Link` global's `props` `DictRef` into an owned `serde_json::Map` and send it down an `mpsc::channel` — no graph-building logic runs on the PipeWire thread-loop's own thread. A separate plain `std::thread` ("the assembler") owns a `HashMap<id, (object_type, props)>` built from that channel, debounces bursts (200ms quiet / 400ms cap — the same shape `run_pw_dump_monitor` already used for `pw-dump -m` line events, just driven by real registry events instead), and on each settle rebuilds the graph and pushes it to `cached_graph` + the stored `GraphListener` if it changed.
  - **The rebuild step deliberately reuses `pw_dump::normalize` and `graph_enrich` completely unchanged**, rather than re-deriving the node/link classification, label-heuristic, and link-to-`current_target` logic against `DictRef` from scratch: a registry `global` event's `props` dict carries the exact same key/value space `pw-dump`'s own JSON `info.props` does (`media.class`, `node.name`, `audio.channels`, `node.rate`, `link.output.node`, ...), so each live object is translated into a synthetic `PwDumpObject { id, object_type, info: Some(json!({"props": props})) }` and fed through the existing, already-tested `normalize()` unchanged. This was a deliberate simplification found during implementation, not the originally-assumed scope — the research spike this was scoped from expected needing to reimplement `pw_dump.rs`'s ~400 lines of classification/labeling logic against `DictRef`; reusing it directly instead means every existing `pw_dump.rs` unit test (HDMI/Analog/Microphone label heuristics, virtual-vs-physical classification, `pipe-deck-*`/`effect_output.*`/`effect_input.*` hiding, sample-rate/channels extraction) is still the acceptance criteria for the native path too, with zero duplicated logic to keep in sync.
  - **`pactl` enrichment (`graph_enrich::enrich_graph_from_pactl`) is explicitly *not* replaced** — this ticket only replaces the `pw-dump` transport, not the separate `pactl`-shellout pass that supplies most volume/mute and some routing-target data (out of scope; a future #8 sub-issue's job). Every rebuild still runs it, same as `enumerate_pipewire()` always did.
  - **Registry `global`/`global_remove` only fires on object announce/removal, never on an existing node's param changes** (e.g. a volume change made in another app) — a real behavioral gap relative to `pw-dump -m`, which re-emits its whole snapshot on essentially any object change. Rather than adding native per-node param listeners (meaningfully bigger scope, arguably #413's territory), the assembler thread also re-enriches-and-notifies on a plain 1-second timer identical in cadence to the old poll-loop fallback — so real topology changes now push instantly (200-400ms) while volume/mute-only external changes still surface within the same ~1s bound the app already had, not worse.
  - **`Format` param (negotiated sample rate) has no cheap registry equivalent** — `pw_dump.rs::audio_sample_rate` already preferred `info.params.Format[0].rate` (pw-dump's own deeper per-node introspection) and fell back to the `node.rate` prop fraction when that wasn't populated yet. The native path only ever has the `node.rate` fallback available (a real per-node `Format` param round trip is an async `enum_params`+callback exchange per node, deliberately not built here) — accepted as a known, pre-existing imprecision rather than new regression, since `pw-dump`'s own JSON already fell back to the same thing whenever a node hadn't run yet this session.
  - **`NativeGraphWatcher`'s PipeWire-owned fields (`ThreadLoopRc`/`ContextRc`/`CoreRc`/`RegistryRc`/the registry `Listener`) are wrapped in `ManuallyDrop` and never explicitly torn down** — confirmed against a real session that normal `Drop` (whatever field order Rust picks) while the thread loop's background thread may still be running produces `impl_ext_end_proxy called from wrong context, check thread and locking` from libpipewire (caught by running `pipe-deck-cli graph` locally, whose one-shot `main()` runs real destructors on clean exit, unlike the GUI/daemon processes which reach `std::process::exit` without ever unwinding this far). Matches `native_host.rs`'s own documented resolution to the same class of problem (never call `pw::deinit()`, let process exit reclaim everything) rather than attempting exact cross-thread teardown ordering.
  - `LinuxPipeWireBackend::new()` tries `NativeGraphWatcher::start()` (blocking up to 2s for the first debounced build, so a caller sees the same "populated graph on return" behavior as the old synchronous `enumerate_pipewire()` seed) and keeps it in a `native_graph: Option<NativeGraphWatcher>` field; on failure (PipeWire unreachable at construction), falls back to the original `pw-dump`-shellout `fetch_graph`/`run_pw_dump_monitor`/`run_poll_loop` path entirely unchanged, gated on `self.native_graph.is_none()`. `fetch_graph()` becomes a plain `cached_graph` read (no shellout) when the native watcher is active, since the assembler already keeps it fresh continuously.
- Constraints: this covers graph fetch/subscribe only. Node lookup (`pw_cli::find_node_id_by_name`'s own `pw-dump` shellout), port linking (`pw_link.rs`), and mixer/virtual-device management (`pactl/*`) are unchanged, tracked as separate #8 sub-issues (#411/#412/#413) that can build on this connection but weren't required to land it.
- Rationale: proves the thread-loop/registry-event pattern end-to-end (validated against a real session: `pipe-deck-cli graph` returns correct real-device data, and a live `#[ignore]`d test confirms a `pw-cat` stream's appearance/disappearance reaches a subscribed listener in well under a second, versus the old worst-case ~1s poll) while keeping the actual code-churn and risk surface small by reusing `pw_dump`/`graph_enrich` as-is — exactly the "spike first, prove the pattern, don't rewrite everything at once" approach #8 itself asked for.

### PD-041 GUI-Process Node Lookup Reuses PD-040's Live Registry Index; Daemon-Side Lookup Is Explicitly Untouched

- Status: Accepted
- Context: #411 (#8's second sub-issue) proposed retiring `pipewire::pw_cli::find_node_id_by_name`'s `pw-dump`-shellout workaround now that PD-040 gives `LinuxPipeWireBackend` a persistent registry connection — "node ids come from the live event stream instead of a re-query." `find_node_id_by_name`/`find_node_ids_by_names` have call sites in two different *processes*: the GUI (`core/engine/effects_ops.rs`'s Live Params fast path, `backend/linux/live.rs`'s latency-ping bulk lookup) and the daemon (`pipewire/native_host.rs`, for its own hosted filter-chain nodes). Only the GUI-process call sites can actually reuse PD-040's connection — it lives inside `LinuxPipeWireBackend`, which only the GUI binary constructs; the daemon has its own, separate `NativeHost` connection (see PD-027's addendum) with no live index of its own.
- Decision:
  - `pw_registry.rs` gains a `node.name -> id` index (`NativeGraphWatcher::find_node_id`/`find_node_ids`) built from the *same* registry events PD-040 already receives — deliberately over every live Node, not filtered the way `pw_dump::normalize`'s UI-facing graph is, since the actual names callers need to resolve (`pipe-deck-*` virtual devices, `effect_output.*`/`effect_input.*` shadow nodes) are exactly the ones `normalize` hides. Updated per-event inside `apply_event`, not gated behind the graph's own 200ms/400ms debounce, to keep the miss window (a node created so recently its registry event hasn't been processed yet) as small as possible.
  - New `AudioBackend::find_live_node_id(&self, node_name) -> Result<Option<u32>, BackendError>` trait method, default-implemented as a straight call to `pw_cli::find_node_id_by_name` (so `MockAudioBackend`/`StubBackend`/`EmptyAudioBackend` are unaffected — same behavior as before, since none of them override it). `LinuxPipeWireBackend` overrides it: check `native_graph`'s index first, fall back to the same `pw-dump` shellout on a miss (native watcher absent, or the node's registry event genuinely hasn't landed yet) — correctness never depends on the index being complete, only latency does.
  - `core/engine/effects_ops.rs::set_effect_chain_live_params` now calls `self.adapter.find_live_node_id(...)` instead of `pw_cli::find_node_id_by_name(...)` directly. `backend/linux/live.rs::measure_latency_ping_live` takes `Option<&NativeGraphWatcher>` (from `self.native_graph.as_ref()`, threaded through from its `AudioBackend::measure_latency_ping` trait method), resolves what it can from `find_node_ids`, then falls back to the bulk `pw_cli::find_node_ids_by_names` shellout for whatever's still missing — a partial-hit-then-fallback shape, not all-or-nothing.
  - **`pipewire/native_host.rs`'s own two `find_node_id_by_name` call sites (daemon process) are deliberately left untouched.** `pipewire/` is explicitly "not part of the `AudioBackend` boundary" (issue #74's territory, separate from #8's `backend::linux` migration), and more concretely, the daemon has no access to the GUI's `LinuxPipeWireBackend`/`pw_registry` connection at all — they're different OS processes. Giving the daemon's own `NativeHost` connection an equivalent live index (mirroring this same pattern against its own registry) is a plausible, structurally similar follow-up, but a distinct piece of work with its own process/lifecycle to reason about — not silently folded into #411, and not required for #411 to deliver real value at the GUI-process call sites it does cover.
- Constraints: `find_live_node_id`/`find_node_ids` never guarantee a hit even for a real, currently-live node — a node created within the last debounce/coalesce window may not have reached the index yet, which is why every call site keeps its `pw-dump`-shellout fallback rather than treating a miss as authoritative. The daemon-side workaround this ticket's parent issue also named is explicitly out of scope, per the above — not a partial implementation, a deliberate boundary.
- Rationale: reuses PD-040's connection instead of standing up a second one in the same process (wasteful, and against the "keep the index lookup-friendly for #411 to reuse" note PD-040's own research already flagged), while being honest that "process" is the real scope boundary here, not "does a workaround still exist somewhere" — `native_host.rs`'s use of the same workaround is a different subsystem with a different owning connection, not an oversight.

### PD-042 Native Port Linking Lives Behind Its Own Process-Wide Connection, Not `LinuxPipeWireBackend`'s

- Status: Accepted
- Context: #412 (#8's third sub-issue) proposed replacing `pw_link.rs`'s `pw-link -o`/`-i`/`-l` port discovery and `pw-link src dst`/`-d` link creation/teardown with native `pw::registry` port enumeration and `pw::link::Link` creation. Unlike #410/#411, `pw_link.rs`'s public functions are called from many places with no single natural owner to thread a connection reference through: `backend/linux/live.rs`, `virtual_mic_mix.rs`, `pactl/routing.rs`, `pactl/virtual.rs`, `graph_routing.rs`, `split_sink.rs`, `virtual_devices.rs`, and even `core/engine/effects_ops.rs`/`processing_node_ops.rs` (which already import `backend::linux::pw_link` directly, a pre-existing exception to the "core never names `backend::linux`" guiding rule this ticket didn't try to fix). PD-040 explicitly considered and rejected a process-wide `OnceLock` for the graph watcher because `LinuxPipeWireBackend` already had "a single, naturally long-lived owner" — that reasoning doesn't hold here.
- Decision:
  - New module `backend/linux/pw_link_native.rs`, structurally parallel to `pw_registry.rs` (same `ThreadLoopRc`/`ContextRc`/`CoreRc`/`RegistryRc` lifecycle, same never-torn-down `ManuallyDrop` fields, same rationale), but reached via a process-wide `static CONNECTION: OnceLock<Option<Connection>>` — `native_host.rs`'s own pattern (`NATIVE_HOST: OnceLock<Mutex<NativeHost>>`), picked here specifically because this module's callers have no shared owner, unlike PD-040's case.
  - The connection's assembler thread indexes every live `Node`/`Port`/`Link` global into a plain `Index { node_ids, node_names, ports, links }` — `ports` and `links` are new; `pw_registry.rs`'s own index only ever tracked nodes. Applied per-event with no debounce (unlike the graph watcher's rebuild, updating a hash map entry is cheap enough that batching would only add latency), same "smallest possible miss window" reasoning #411 used for its own `name_index`.
  - Every public function in `pw_link_native.rs` mirrors one in `pw_link.rs` (`link_capture_source_to_virtual_input`, `link_sink_monitor_to_target`, `is_sink_monitor_routed_to`, `disconnect_stale_output_links`, ...) but returns `Option<...>` — `None` means "couldn't be attempted natively" (connection never started, or either endpoint's node/ports aren't indexed yet) and `pw_link.rs`'s same-named function falls straight through to its own unchanged CLI body; `Some(_)` means the native attempt ran to completion and its result is used as-is. Same "fall back to the shellout for what's missing" contract #411 established, applied per-call rather than once at startup.
  - Port pairing (`pw_link_native::pair_ports`) is a byte-for-byte behavioral port of `pw_link.rs::pair_capture_ports` — sort by port name, cycle the shorter side across the longer — operating on `(port id, port name)` instead of `"system_name:port_name"` strings. This is a hard requirement carried over from #412's own ticket text, not just preserved incidentally: the mono-fallback/Bluetooth-HSP single-port-target case is why this cycling exists at all, and losing it silently breaks device pairing that currently works.
  - Link creation goes through the well-known `link-factory` (the same one the `pw-link` CLI itself uses) with `object.linger => "1"` in the properties, matching `pipewire-rs`'s own `create-delete-remote-objects` example. Without it, the `Link` proxy `create_object` returns would tear the link back down the instant this code drops it (`Proxy::drop` calls `pw_proxy_destroy`) — `object.linger` is what lets a link created here persist exactly like one `pw-link src dst` creates and then exits without tearing down, so no proxy needs to be retained afterward. Link teardown goes through `registry.destroy_global(link_id)` (found via the `links` index, keyed by the link's own global id, not by proxy) — the same mechanism `pw-link -d` itself uses, so it works on a link regardless of which client created it.
- Constraints: node names are indexed as a plain `HashMap<String, u32>`, last-write-wins on a collision — the same limitation #411's `name_index` already accepted, not a new one. A verified failure mode during implementation: two leftover `pipe-deck-*` modules sharing the same `system_name` (from repeated test runs that failed before reaching cleanup) made `node_id()` resolve to whichever registered last, not necessarily the one a caller meant — not a defect in this design, but a reminder that duplicate-named live nodes are already an accepted edge case, not one #412 introduces.
- Rationale: proved end-to-end against a real session (`#[ignore]`d `pw_link_native::live_tests`, run manually): creates two disposable virtual devices, links them via the native path (asserted `Some(_)`, not a silent CLI fallback), independently verifies the link's existence via a fresh `pw-link -l` parse (not this module's own index), disconnects natively, and re-verifies removal the same independent way. Keeping the `Option`-returning/fallback shape rather than deleting the CLI implementation outright limits the actual risk surface to "the native path might not fire" (safe, falls back) rather than "the native path might silently produce wrong routing with no CLI backstop."

### PD-043 Native Volume/Mute Is Scoped to Devices Only, and Write-Only

- Status: Accepted
- Context: #413 (#8's fourth and largest sub-issue) covers `pactl/*`'s ~1750 lines: volume/mute, virtual device (module) lifecycle, sink-input routing/moves, and the holding-sink teardown dance — the ticket itself flags this as too big for one PR ("consider whether this lands as one PR or splits further ... once the shape of the native replacement is clearer"). This decision covers the first slice only: device volume/mute.
- Decision:
  - New module `backend/linux/pw_mixer_native.rs`, structurally parallel to `pw_link_native.rs` (own process-wide `OnceLock` connection, per PD-042's identical reasoning — `pactl/mixer.rs`'s callers span `live.rs`/`pactl/virtual.rs` with no single shared owner), but only needs a `node.name -> id` index, not port/link tracking.
  - Volume/mute are pushed via `Node::set_param(SPA_PARAM_Props, ...)` against a bound `Node` proxy — the exact bind/set/drop-under-one-`thread_loop.lock()` shape `pipewire/native_host.rs::set_param` already established for live effect params, applied here to the standard `SPA_PROP_channelVolumes`/`SPA_PROP_mute` every sink/source node exposes instead of a filter-chain's custom control ports.
  - **Percent-to-linear-amplitude uses a cubic curve (`(percent/100)³`), not a plain linear scale.** `SPA_PROP_channelVolumes` is raw linear amplitude, but the percent this codebase (and `pactl`, what set volume before this) works in is cubic — confirmed against `pactl/parse.rs`'s own existing test fixture (`64860 / 99% / -0.27 dB`: `0.99³ ≈ 0.9703`, `20·log10(0.9703) ≈ -0.261 dB`, matching within rounding) and independently reconfirmed live during this ticket's own verification (see below). Sending linear `percent/100.0` directly would make every native volume change sound audibly louder than the same percent set via `pactl` — a real loudness regression the moment the native and CLI paths disagree, not a cosmetic mismatch.
  - **Scoped to device volume/mute only** (`set_device_volume`/`set_device_mute`/`set_sink_volume_by_name`/`set_sink_mute_by_name`, `pactl/mixer.rs`'s callers resolved via `node.name`). **Stream volume/mute (`set_stream_volume`/`set_stream_mute`, sink-inputs/source-outputs) is deliberately left on `pactl`** — those are resolved via a pactl sink-input/source-output *index* from `pactl/parse.rs`'s own text parsing, a separate, not-yet-ported correlation problem (does a Pulse-compat sink-input index reliably equal the underlying node's native id? not verified here) rather than a blind extension of this same technique.
  - **Volume/mute *reads* (`sink_volume_percent`/`sink_mute_state`, used to reflect a per-mix-source feed sink's live gain back into the UI) are also left on `pactl`.** Every native `set_param` call site in this codebase, including this one, is write-only — reading a live node's current `Props` needs `Node::enum_params` plus Pod *deserialization*, a capability with no precedent here (this codebase's only existing Pod work, `native_host.rs`'s `EffectProps`, is serialize-only). Not attempted in this slice.
  - Each public function resolves every node id it needs (primary, plus the `{sink}.monitor` node for a virtual output's fan-out, if applicable) before doing anything — `None` (full fallback to the existing `pactl` body) unless every id resolves, so a single logical volume/mute change is never a native/CLI hybrid.
- Constraints: `set_stream_volume`/`set_stream_mute` and `sink_volume_percent`/`sink_mute_state` stay exactly as they were before this ticket — not a regression, a deliberately narrower slice than #413's full scope, consistent with the ticket's own call to split.
- Rationale: verified live (`#[ignore]`d `pw_mixer_native::live_tests::sets_volume_and_mute_natively_matching_pactls_own_readback`, run manually): creates a disposable virtual device, sets volume to 42% and mute via the native path (asserted to actually run, not silently fall back), and reads both back through `pactl/mixer.rs`'s own `sink_volume_percent`/`sink_mute_state` — a completely independent pipeline (a fresh `pactl list sinks` shell + text parse) that would have caught a cubic-curve mistake no in-process assertion against this module's own state could.

### PD-044 Virtual Device Creation Uses `adapter`/`support.null-audio-sink`, Not Module Loading

- Status: Accepted
- Context: #422, a sub-issue split off #413 (native mixer + virtual device management) after volume/mute (PD-043) shipped as the first slice. Covers `create_virtual_output`/`create_virtual_input`/`restore_virtual_device`/`remove_virtual_device` — the create/remove path `pactl/virtual.rs`'s `create_null_sink`/`create_virtual_source`/`unload_module` currently serve via `pactl load-module module-null-sink`/`unload-module`.
- Decision:
  - **`module-null-sink` is not a real PipeWire module** — unlike `libpipewire-module-filter-chain` (which `pipewire/native_host.rs` genuinely loads via `pw_context_load_module`), it's Pulse-compat terminology `pipewire-pulse` itself implements. Confirmed live (`pw-dump`) that what it actually creates is a single `adapter`-factory node with `factory.name = support.null-audio-sink` — exactly the construct `/usr/share/pipewire/pipewire.conf`'s own commented-out example documents for a virtual mic. New module `backend/linux/pw_virtual_device_native.rs` creates the same construct directly via `core.create_object::<pw::node::Node>("adapter", ...)`, the identical `create_object` mechanism PD-042's `pw_link_native.rs` already uses for links — no module-loading machinery needed.
  - **The `capture_*`/`input_*` (vs. `playback_*`/`monitor_*`) port-name split `pw_link.rs` depends on for virtual inputs isn't set explicitly anywhere** — it falls out of `support.null-audio-sink` purely from `media.class` (`Audio/Source/Virtual` vs. `Audio/Sink`). Verified by comparing a `pactl`-created virtual mic's live `pw-dump` output against this module's own `Audio/Sink` test node side by side before writing any Rust, then re-confirmed end-to-end through the real `AudioBackend::create_virtual_input`/`create_virtual_output` trait methods (`pw_virtual_device_native::live_tests`).
  - **Object lifetime uses `object.linger => "1"`, not a retained module handle.** `native_host.rs`'s filter-chain modules are unloaded via a retained `*mut pw_impl_module` pointer, because a `pw_context_load_module` handle has no other identity. A created `Node` doesn't need that: `object.linger` (the same property PD-042's link creation already relies on) lets it outlive this connection's own proxy going out of scope, and — unlike a retained handle — it also survives a full process restart, since nothing about it depends on this process staying alive. Removal re-resolves the node's *current* global id by name (this module's own registry index) and calls `registry.destroy_global(node_id)`, the same mechanism PD-042 uses to tear down a link regardless of which process created it.
  - `pactl/virtual.rs::create_null_sink`/`create_virtual_source` try the native path first; on success, the returned `module_id` string is set to a `"native:{system_name}"` sentinel rather than a real `pactl` module index (there isn't one — confirmed live that a natively-created node does *not* appear in `pactl list modules short`, even though it does appear in `pactl list sinks/sources short`). `unload_module` dispatches on that prefix to the native `destroy_global` path; anything without the prefix (a real `pactl`-created module, or a native attempt that fell back) takes the unchanged `pactl unload-module` path.
- Constraints: **deliberately scoped to the create/remove path only.** Existence checks (`sink_exists`/`source_exists`/`pipe_deck_device_is_live`), module discovery after a restart (`list_pipe_deck_modules` — still correct for natively-created nodes, since it's driven by `pactl list sinks/sources short`, not `list modules short`), description-sync-via-recreate, the holding sink, and feed-sink lifecycle all stay on `pactl` unchanged. Sink-input routing/moves and the holding-sink teardown dance remain explicit, not-yet-started follow-on work under #413, same as the ticket's own text already called out as needing its own design pass.
- Rationale: verified live end-to-end through the real trait methods (`#[ignore]`d `pw_virtual_device_native::live_tests`, run manually): `create_virtual_output`/`create_virtual_input` each produce a device with the correct port topology (checked via a fresh `pw-link -o`/`-i` parse, independent of this module's own index) and Pulse-compat visibility (`pactl`'s own `sink_exists`), then `remove_virtual_device` tears it back down, re-verified the same independent way.

### PD-045 Native systemd Control via `zbus`, No CLI Fallback, Reduced Test Fakeability

- Status: Accepted
- Context: #425 — `daemon/mod.rs`'s `run_systemctl` shelled out to `systemctl --user enable/disable/is-enabled/is-active/daemon-reload` for the background restore-on-login service, parsing exit codes/stdout. Not part of epic #8 (native PipeWire backend migration) — a different subsystem (systemd, not audio) — filed and landed standalone.
- Decision:
  - New module `daemon/systemd.rs` talks directly to `org.freedesktop.systemd1.Manager`/`.Unit` over the session D-Bus via `zbus`'s blocking API (`zbus::blocking::Connection::session()` + `#[zbus::proxy]`-generated proxies), pure Rust — `zbus` doesn't link `libdbus` at all (a `libdbus-sys` dependency does already exist in the tree, but it comes from `tao`/`tauri`, pre-existing and unrelated).
  - **No CLI fallback**, unlike every `backend::linux` native module from #8's migration. `systemctl` is itself just a D-Bus client for this exact API — if the session bus is unreachable, `systemctl --user` would fail identically, so a fallback would only add code, not resilience.
  - Each function (`reload`/`enable_and_start`/`disable_and_stop`/`is_enabled`/`is_active`) opens its own short-lived connection rather than caching one process-wide — unlike the PipeWire native modules (persistent connections justified by being on hot, frequently-hit paths), unit control happens a handful of times per app session at most, so a fresh connection per call is cheaper to reason about than adding lifecycle management for a connection that would mostly sit idle.
  - `enable_and_start`/`disable_and_stop` map to `EnableUnitFiles`+`StartUnit` / `StopUnit`+`DisableUnitFiles` respectively (`mode = "replace"`, matching `systemctl`'s own default job mode); `is_enabled`/`is_active` map to `GetUnitFileState` / `GetUnit`+the `Unit` interface's `ActiveState` property, each tolerating any D-Bus error (unit never installed, no session bus, ...) as `false` — the same tolerance `run_systemctl(...).unwrap_or(false)` had.
  - **Test coverage cost, accepted deliberately, not silently dropped.** The retired `run_systemctl` had a fake `systemctl` binary on `PATH` recording every invocation (`daemon::mod::tests`' `FakeSystemctl`, `pipe-deck.rs`'s own copy) — trivial to fake because it was a subprocess. A D-Bus service has no equivalent drop-in fake without standing up a mock `org.freedesktop.systemd1` service on a private bus, which wasn't attempted here. `daemon::mod::tests`' five call-order-asserting tests (install/enable/disable/uninstall) were removed rather than pointed at the real bus, because every one of them ultimately targets the literal `pipe-deck-daemon.service` unit name — running them for real against `zbus` on a machine with that service actually installed and enabled would disable/stop it for real, exactly the hazard `FakeSystemctl`'s own doc comment cited PR #256 for. `pipe-deck-cli`'s `handle_cleanup_removes_daemon_unit_and_purges_config_when_requested` test hits the same issue and was marked `#[ignore]` (run manually) rather than removed, since its file/config-purge assertions are still real signal. The actual new D-Bus call surface is instead covered by an `#[ignore]`d live test (`daemon::systemd::live_tests`) against a disposable, uniquely-named unit (never `pipe-deck-daemon.service`) written straight into the *real* `~/.config/systemd/user/` — an env-var-redirected `XDG_CONFIG_HOME` has no effect here, since it's invisible to the already-running systemd --user process this test actually talks to over D-Bus, unlike a plain file-write test.
- Constraints: `cargo test`'s default sweep exercises less of the systemd-integration surface than before this ticket — pure file/logic tests (unit-file version-marker parsing, `stale_state_filter`, the no-op-when-missing case) still run automatically; anything that would issue a real enable/disable/start/stop against the production unit name now requires deliberately running an `#[ignore]`d test by hand. This is a real, acknowledged trade for dropping the CLI's free fakeability, not an oversight.
- Rationale: verified live (`#[ignore]`d `daemon::systemd::live_tests::enables_starts_and_reports_state_matching_systemctls_own_readback`, run manually against the sandbox's real user session): installs a disposable unit, exercises the full enable/is-enabled/is-active/disable cycle through this module, and cross-checks the active-state readback against the real `systemctl --user is-active` binary independently at each step — not just this module's own state.

### PD-046 Native Volume/Mute Reads via `Node::enum_params` + Pod Deserialization

- Status: Accepted
- Context: #424, filed as a direct follow-on to #413's first slice (device volume/mute writes, PD-043). That slice's own doc comment flagged the gap: every native `set_param` call site in this codebase, including its own, is write-only — `pactl/mixer.rs`'s `sink_volume_percent`/`sink_mute_state` (used to reflect a per-mix-source feed sink's live gain back into the UI) stayed on `pactl list sinks` text parsing because reading a live node's `Props` needs `Node::enum_params` plus Pod *deserialization*, a capability `libspa` (already a transitive dependency via the `pipewire` crate) provides but this codebase had never exercised.
- Decision:
  - `pw_mixer_native.rs::Connection` gains `query_props(node_id)`, binding a `Node` and issuing `enum_params(0, Some(Props), 0, u32::MAX)` — unlike `set_props` (fire-and-forget), this is a genuine async round trip: `enum_params` doesn't return a value, it triggers a `param` event on a registered listener sometime later. The listener forwards the first `Props` param it sees down an `mpsc` channel; `query_props` releases `thread_loop.lock()` *before* waiting on that channel, since the callback only runs on the thread loop's own internal dispatch thread — holding this process's lock while waiting would deadlock (nothing would ever run the loop far enough to invoke it). Node/listener are bound and dropped each under their own lock acquisition rather than one continuous critical section spanning the wait, which only looks like it contradicts `native_host.rs::set_param`'s "keep bind/use/drop under one lock" rule — that rule is about not letting a proxy outlive the lock while another thread might touch the loop concurrently, not about never unlocking at all; an async wait for a callback the loop's own thread must run is exactly the case where releasing the lock in between is required.
  - The returned Pod is deserialized via `PodDeserializer::deserialize_from::<Value>(pod.as_bytes())` into `libspa`'s generic `Value`/`Object`/`Property` types, then matched for `SPA_PROP_channelVolumes` (`Value::ValueArray(ValueArray::Float(_))`, first channel) and `SPA_PROP_mute` (`Value::Bool`) — no custom Pod-walking code, just `libspa`'s own already-provided generic deserialization.
  - Read-back volume converts through the *inverse* of the cubic curve PD-043 established for writes (`linear.cbrt() * 100.0`), so a value `pactl` itself set (not just one this module wrote) round-trips to the same percent a person would see in `pactl list sinks`' own `%` column.
  - Same `Option`-returning contract as every other native call in this migration: `None` (fall back to `pactl`) unless the connection is up and the node is indexed; `Some(Ok(None))` if the query itself succeeded but the node's `Props` didn't carry the property asked for.
- Constraints: stream volume/mute (sink-input/source-output index resolution) is still out of scope, unchanged from PD-043 — a separate porting problem, not something this ticket's Pod-deserialization work incidentally unblocks.
- Rationale: verified live (`#[ignore]`d `pw_mixer_native::live_tests::reads_volume_and_mute_natively_matching_pactls_own_readback`, run manually): sets a disposable virtual device's volume/mute via `pactl` directly (not this module's own writer, specifically so the read path is checked against a value it had no hand in producing — round-tripping a native write through a native read alone wouldn't catch a read path that just echoed back whatever this module last wrote), then reads both back through `channel_volume_percent`/`mute_state` and confirms they agree with what `pactl` itself set.

### PD-047 Stream Routing Is Native Port Relinking, Not a `pactl` Index Port

- Status: Accepted
- Context: #428, the last remaining slice of #413 (and #8's epic), covering `pactl/routing.rs`'s stream move/clear operations and the holding-sink teardown dance (`live.rs::hold_sink_inputs_for_swap`/`release_held_sink_inputs`). The parent ticket explicitly flagged this as the trickiest part of #413, needing its own design pass rather than a blind port — `move-sink-input`/`move-source-output` operate on a `pactl` sink-input/source-output *index*, resolved via `pactl/parse.rs`'s own text-parsing of `pactl list sink-inputs`/`list source-outputs`.
- Decision:
  - **A stream is just another PipeWire node** — confirmed live (`pw-dump`) before writing any code that `core::models::Stream.system_name` is already populated from the live node's `node.name`, exactly like a device. "Moving a stream to a new target" is therefore not fundamentally a `pactl`-index operation at all — it's the same disconnect-old/link-new port relink `pw_link_native.rs` (#412) already built for device-to-device routing, just *exclusive* (disconnect every existing link first, not only the ones to one particular target) since a stream draws from or sends to exactly one place, unlike a sink's monitor fan-out.
  - `pw_link_native.rs` gains `disconnect_all_inputs` (the input-side counterpart to `disconnect_sink_monitor`, needed because every earlier query in that module starts from a known *output* side) and `route_playback_stream`/`route_capture_stream`, each composing "disconnect everything, then link fresh" from primitives that already existed. Neither prefix-filters the stream's own port names (unlike every device-shaped "target" elsewhere in this module) — an arbitrary app's ports follow no Pipe Deck naming convention (confirmed live: `pw-cat`'s ports are `output_FL`/`input_MONO`, nothing like `playback_*`/`capture_*`).
  - `pw_link.rs` gains the same three functions as genuine native-try/`pw-link`-CLI-fallback public wrappers — not `pactl`-based fallbacks. This is a deliberate, different fallback shape from `pactl/routing.rs`'s own remaining index-based path: `pw_link`'s CLI fallback needs only a `system_name` string (no `RuntimeGraph`/`Stream` reference), which is exactly what `live.rs`'s holding-sink dance has to work with and a `pactl`-index-based fallback could not have provided there.
  - `pactl/routing.rs`'s three move/clear functions now call `pw_link::route_playback_stream`/`route_capture_stream` directly whenever `stream.system_name` is `Some` — which already carries native-or-CLI fallback internally, so the original `pactl move-sink-input`/`move-source-output` + index resolution is now reached only in the one case that genuinely still needs it: a stream whose live `node.name` came back empty (structurally possible per `pw_dump.rs`'s own stream normalization, though not observed live).
  - **The holding-sink dance's discovery and move steps are both now stream-name-keyed, not `pactl`-index-keyed.** `AudioBackend::hold_sink_inputs_for_swap`/`release_held_sink_inputs`'s trait signature changed from `Vec<u32>` (opaque `pactl` sink-input indices) to `Vec<String>` (each held stream's own `system_name`) — an already-opaque-to-`core::engine::effects_ops` handle either way, so the type change touches only the four trait implementors (`LinuxPipeWireBackend`, `MockAudioBackend`, `StubBackend`, the default `EmptyAudioBackend` impl), not `effects_ops.rs` itself. Discovery reuses `pw_link::list_capture_sources_for_sink` verbatim (already built for #412's capture-source-into-a-mix discovery — the identical query, "what's linked into this sink's `playback_*` ports," works for stream discovery too) rather than `pactl::sink_input_indices_on`; the move itself goes through a new `move_stream_with_retry` (`live.rs`) built on `pw_link::route_playback_stream`, replacing `pactl::move_sink_input_with_retry`'s index-based retry loop.
  - The holding sink itself (`pactl::HOLDING_SINK_NAME`) is unchanged — an ordinary virtual output device, already natively creatable via #422.
- Constraints: `pactl/routing.rs`'s default-sink/source lookup (`get_default_sink_name`/`get_default_source_name`, used to resolve a `clear_stream_target` fallback) stays on `pactl get-default-sink`/`get-default-source` — reading PipeWire's own `default` metadata object natively is a distinct, not-yet-touched capability (a `Metadata` proxy, not a `Node`), out of scope for this slice.
- Rationale: verified live end-to-end with real `pw-cat` streams (not just disposable virtual devices) at every layer: `pw_link_native::live_tests::routes_a_playback_stream_between_targets_exclusively`/`routes_a_capture_stream_between_sources_exclusively` (a looped `pw-cat --playback`/`--record` process re-routed between two disposable targets, cross-checked via a fresh `pw-link -l` parse that the old link is actually gone, not just that the new one exists) and `live::live_tests::holds_and_releases_a_real_stream_across_a_simulated_swap` (drives the actual `AudioBackend::hold_sink_inputs_for_swap`/`release_held_sink_inputs` trait methods directly against a real stream, confirming the full park-on-holding-sink/restore cycle). All three `#[ignore]`d, run manually.

### PD-048 Native Node Lookup for the Daemon's Own Connection

- Status: Accepted
- Context: #430, a sub-issue of epic #8 filed as the explicitly-deferred follow-up PD-041 called out: "a plausible, structurally similar follow-up ... not required for #411 to deliver real value at the GUI-process call sites it does cover." #411 gave `LinuxPipeWireBackend` (GUI process) a live `node.name -> id` index so `find_live_node_id` checks it before falling back to a `pw-dump` shellout. `pipewire/native_host.rs`'s own two `find_node_id_by_name` call sites (`load_chain`'s port-visibility poll, `set_param`'s node lookup) were left untouched, since the daemon has no access to the GUI's connection at all — different OS processes, each with its own separate PipeWire connection (`native_host.rs`'s own, per PD-027's addendum).
- Decision:
  - `native_host.rs`'s existing `NativeHost`/`host()` `OnceLock` connection gains a registry `global`/`global_remove` listener building a `node_ids: Arc<Mutex<HashMap<String, u32>>>` index — the same shape `pw_registry.rs::NativeGraphWatcher` (#411) built for the GUI process, registered once at connection creation and kept continuously updated for the connection's whole life, not a listener registered fresh per call (`set_param`'s own pre-existing doc comment already explained why that specific mistake caused issue #303: a fresh listener only ever sees a `global` announcement once, so one registered after a node already exists never sees it).
  - `node_ids` is a plain `Arc<Mutex<..>>`, deliberately *not* protected by `NATIVE_HOST`'s own outer `Mutex` — the registry callbacks run on the thread loop's own internal dispatch thread, which must be able to update the index without acquiring `NATIVE_HOST`'s mutex, since `load_chain`/`set_param` already hold that mutex while doing other `pw` work; a callback trying to re-acquire it recursively would risk a deadlock this independent lock avoids entirely.
  - `load_chain`'s port-visibility poll and `set_param`'s node lookup both check `node_ids` first, falling back to the existing `pw_cli::find_node_id_by_name` `pw-dump` shellout on a miss — the same "fall back to the shellout for what's missing" contract #411 established, not a hard cutover.
- Constraints: none beyond what #411 already accepted — a node created within the last instant may not have reached the index yet, so every call site keeps its shellout fallback rather than treating a miss as authoritative.
- Rationale: verified live with a new in-process `#[ignore]`d test (`pipewire::native_host::live_tests::load_chain_and_set_param_resolve_the_node_via_the_native_index`, run manually) — unlike the pre-existing `daemon::ipc::client::live_tests` (which spawn a real daemon *subprocess* and can only observe `load_chain`/`set_param`'s pass/fail return value, indistinguishable between the native and shellout-fallback paths), this test runs in the same process as `native_host.rs` itself and inspects `host()`'s own `node_ids` index directly via a test-only accessor — confirming both the filter-chain's playback node and its main device node are genuinely resolved through the native index, including well after creation (past the old per-call-listener's narrow announcement window), not silently through the fallback the whole time.

### PD-051 Native `pw_filter` Hand-Written DSP Spike: Feasible, With a New #303-Adjacent Gotcha

- Status: Accepted (research spike concluded; no production change)
- Context: #86 (compressor dynamics) has been blocked/research-stage since filing — no PipeWire version ships a builtin envelope-following dynamics primitive, and PD-017 bars FFmpeg/third-party LADSPA as a substitute after the #64 incident. #509 asked whether Pipe Deck could instead run genuinely hand-written, compiled-in DSP (an envelope follower, attack/release, gain reduction — not a config-driven builtin) inside a native `pw_filter` process() callback, since PD-027/#148 already proved a raw PipeWire connection from a long-running process can host real objects in the live session — just never yet for custom per-sample DSP, only for loading PipeWire's own `module-filter-chain` builtins (`pipewire/native_host.rs`).
- Decision: a throwaway example binary, `src-tauri/examples/pw_filter_dsp_spike.rs` (plain example, no feature gate needed — `pipewire` is a mandatory dependency as of PD-029's cutover, unlike PD-027's spike which needed one to keep `pipewire-rs` opt-in), implements a hand-written hard limiter (`out = clamp(in, -threshold, threshold)` — the "even just a hard limiter, as a first proof point" scope #509 explicitly called out) and runs it against a real PipeWire 1.5.85 session. Findings:
  - **`pipewire-rs` 0.10 has no safe wrapper for `pw_filter`** — only `pw_stream` is bound in the high-level crate. The raw `pw_filter_*` C API (including the convenience `pw_filter_get_dsp_buffer`/`format.dsp`-prop port shape PipeWire's own `audio-dsp-filter.c` example uses, which sidesteps manual SPA pod format negotiation entirely) is nonetheless present in `pipewire::sys`, since `pipewire.h` transitively includes `filter.h` and the crate's bindgen allowlist is a permissive `pw_.*`. Building on this is the same kind of raw-FFI-alongside-safe-wrappers pattern `native_host.rs` already uses for `pw_context_load_module`, not a new category of risk for this codebase.
  - **It works end-to-end against the real session.** The filter's node and both DSP ports (one input, one output) appeared as real, externally-visible ports (confirmed via `pw-link -o`/`-i` from a separate process, not just this process's own bookkeeping). A loud test tone played into the system's real default sink via `pw-cat --target`, `pw-link`ed from that sink's real `monitor_FL` into the filter's input port, was measurably limited by genuine hand-written per-sample math running inside `process()`: peak input 0.9 (matching the rendered tone exactly), peak output pinned to the 0.3 threshold, with 96,165 of 168,960 samples (~57%) actually clamped. Teardown (`pw_filter_disconnect`/`pw_filter_destroy` plus unloading a throwaway null-sink module used as the output's downstream consumer) left no orphaned node, port, or module behind across repeated runs.
  - **A new, #303-adjacent scheduling gotcha, found the hard way**: the first working version used a plain `pw::main_loop::MainLoopRc`, manually `iterate()`d in bursts — `process()` was called (131-165 times over ~4.5s), but `spa_io_position.clock.duration` was 0 on *every* call, so zero samples ever actually flowed through the DSP math despite the callback firing. Switching to the same `pw::thread_loop::ThreadLoopRc`-started-once-and-run-continuously fix #303/`native_host.rs` already documents for module-hosted filter-chain instances did **not**, by itself, fix this — duration stayed 0 until the filter's *output* port was also linked to a real downstream consumer (a throwaway mono `module-null-sink`). A `pw_filter` node with a live input link but a completely unlinked output apparently never gets folded into an actively driven quantum at all, a distinct-from-#303 scheduling requirement specific to filter-shaped (both-directions) nodes rather than the sink/source-shaped nodes `native_host.rs` deals with.
  - **RT-safety was straightforward to hold to** for a limiter: `process()` touches only raw pointer arithmetic (`pw_filter_get_dsp_buffer`) and lock-free atomics (`AtomicU32`/`AtomicU64`, including a CAS-loop `atomic_max_f32` for peak tracking) — no allocation, no locking, no syscalls. A real compressor's envelope follower/attack-release state would need per-sample mutable float state (not just monotonic counters), but that's plain non-atomic memory owned by the `process()` closure's data pointer, not anything requiring new RT-safety machinery beyond what this spike already exercises.
- Rationale: the spike's job, same framing as PD-027's, was to convert "is this viable" into "here's what a real implementation has to handle" — it succeeded, with a materially better answer than PD-027's own note that no builtin dynamics primitive exists: first-party DSP compiled into the binary is a real, working path that satisfies PD-015 without an external plugin file or reopening the PD-017 safety question, since there's no arbitrary third-party config being loaded. The #303-adjacent output-linkage gotcha is exactly the kind of "what does production actually need to get right" finding this kind of spike exists to surface cheaply, before a real compressor implementation trips over it in the field. Out of scope here, unchanged from #509's original framing: production compressor UI/params, profile persistence, a real envelope follower/attack-release curve, and closing `core/engine/effects_ops.rs`'s boundary gap for a new `ProcessingNode` kind — #86 can now move from "blocked, no actionable plan" to "buildable on this mechanism," but the actual implementation is separately-scoped future work.

### PD-052 Real Compressor Processing Node: `native_dsp_host` Generalized to Host a Standalone Bus

- Status: Accepted
- Context: #86 (compressor dynamics) was blocked/research-stage until PD-051's #509 spike proved a hand-written `pw_filter`-hosted DSP stage works against a real session. This decision records the follow-through: a real, shippable `ProcessingNodeKind::Compressor` (PD-032's pattern — a first-class graph node, not a device attachment), not just the spike.
- Decision:
  - **`dsp::CompressorProcessor`** (`src-tauri/src/dsp/compressor.rs`) is a real `DspStage`: a classic feedforward compressor — peak envelope follower with independent attack/release one-pole smoothing in the dB domain, a hard-knee gain computer (`threshold_db`, `ratio_x10` fixed-point), and a final linear makeup-gain trim (`makeup_gain_db`). No lookahead/soft-knee, matching the "even a hard limiter is a real proof point" scope PD-051's spike used, now with a genuine envelope rather than an instantaneous clamp. Unit-tested for steady-state gain-reduction accuracy against the closed-form expected value, makeup-gain scaling, silence/non-finite-input safety, and reset behavior.
  - **`pipewire::native_dsp_host` (issue #74) is generalized from mic-only to also host a standalone `ProcessingNode` bus.** Before this, the module's own doc comment claimed it "only implements that capture-direction template" (mic-attached, swap-by-identity: `device_system_name` itself becomes the processed outlet). `load_chain` gained the same `is_input: bool` flag `native_host::load_chain` already has: `is_input = false` keeps `device_system_name` as the plain inlet (nothing pivots — there's no pre-existing device identity to preserve for a processing node) and names the processed outlet `effect_output.<device_system_name>` with no forced `media.class`, mirroring `fx_validate::render_module_args`'s own naming for every other builtin-backed `ProcessingNodeKind`. This means Compressor's `system_name`/output-identity conventions are indistinguishable from Reverb/Widener/etc's at the routing layer — `relink_processing_node_port` and friends needed zero changes to handle the new kind. The daemon IPC message (`LoadDspChain`) and its client/server plumbing thread the same flag through.
  - **A new, #303-adjacent scheduling gotcha, found productionizing the spike's finding for real**: the spike's `MainLoopRc`→`ThreadLoopRc` fix alone wasn't sufficient. A `pw_filter` with a live input link but a completely unlinked output never gets folded into an actively-driven quantum — `process()` fires, but `spa_io_position.clock.duration` stays 0 forever, so zero samples ever flow, silently. Every prior use of `native_dsp_host` (the mic-attached EQ path) always had a real downstream consumer by construction, so this never surfaced before. Documented in `docs/developers/Adding_PipeWire_Effects.md` as a gotcha for the next DSP-backed kind.
  - **`load_processing_node`'s `Compressor` arm bypasses `fx_validate::preflight`/`fx_capability` entirely** (unlike every other DSP-backed `ProcessingNodeKind`, which preflight-check builtin-filter availability before loading) — there's no builtin-availability question to ask for code that's always compiled into the binary. It calls `NativeHostClient::load_dsp_chain` directly and unconditionally.
  - **The legacy `compressor: DynamicsStage` field on `EffectChainConfig` stays permanently blocked and untouched** — same precedent `ProcessingNodeKind::Limiter` (#311) already set for the parallel `limiter: DynamicsStage` field: a new DSP-backed `ProcessingNodeKind` is a clean, independent addition, not a promotion of the old device-attached dynamics concept. `StubEffectKind::Compressor` is removed outright (no migration for a stale persisted stub, same precedent `reverb_delay`/`limiter`/`hpf`/`stereo_widener`'s own graduations set — accepted pre-1.0 alpha config-compat breakage, not treated as a gap).
  - `config::store::update_processing_node_compressor`, `core::engine::processing_node_ops::update_processing_node_compressor_params` (+ Tauri command), and `AudioBackend::set_processing_node_compressor_params` (real `LinuxPipeWireBackend` impl via `native_dsp_host::set_live_chain`, `MockAudioBackend` impl) all follow the exact per-kind pattern every other `ProcessingNodeKind` already established — `set_processing_node_bypassed`'s per-kind dispatch match gained a `Compressor` arm the same way.
  - **`dsp::DspChain::from_config` now honors `config.bypassed`** (previously silently ignored for every kind, including the pre-existing EQ5Band-via-`native_dsp_host` path) — returns an empty (pure passthrough) chain when bypassed, mirroring every builtin-module renderer's own "bypass = neutral params" convention, since a real DSP stage has no equivalent "neutral params" shape to render into config text instead. A genuine, incidental bug fix for the EQ5Band mic-attached bypass toggle, not just new Compressor-specific behavior.
  - Frontend: `ProcessingNodeKind`/`ProcessingNodeSpecKind` TS unions, `graphActions.ts`, `NodeTypeIcon.vue`, and a new `RoutingGraphNodeCompressor.vue` (five sliders: Threshold/Ratio/Attack/Release/Makeup Gain, following `RoutingGraphNodeDelay.vue`'s multi-control pattern) all follow the established per-kind template; the context-menu entry moved from `STUB_EFFECT_CATALOG` to the real node catalog, same as every prior graduation.
- Rationale: verified against a real PipeWire session — `compressor_node_round_trips_on_a_real_pipewire_session` (create via a real ephemeral daemon, confirm `NativeHostClient::is_dsp_chain_loaded`, live-update params, remove, confirm unloaded) — plus re-running the pre-existing Reverb/Widener/Pan/EQ5Band live tests and the `native_dsp_host` module's own live tests to confirm the `is_input` generalization didn't regress the mic-attached path. This closes #86 from "blocked, no actionable plan" (its original framing) to shipped: real dynamics processing, first-party DSP, no plugin dependency, satisfying PD-015 without reopening PD-017's safety concern.

### PD-053 Soundboard Overlap Policy Is a Per-Tab Client Boundary

- Status: Accepted
- Context: Issue #408 asks for a per-soundboard-tab choice between the existing overlapping trigger behavior and exclusive playback. The frozen post-#399 main branch instead suppresses a second tile click while a clip is active, and #409 supplies the existing global stop command; the compatibility baseline is therefore the current single-clip behavior, not the issue body's pre-#409 wording.
- Decision:
  - `SoundboardBoard` gains `exclusive_playback: bool`, serialized with every board. Serde defaults a missing field to `true`, so legacy YAML remains loadable and keeps the current restricted behavior; `false` explicitly opts a tab into overlap.
  - The active tab renders an **Exclusive playback** checkbox and saves it through `save_soundboard_board`. New boards and legacy responses that omit the field use the same `true` fallback.
  - At the public tile-click consumer boundary, exclusive mode calls the existing stop command and waits for success before issuing the next play. If stopping fails, the next clip is not started. Overlap mode issues the next play directly and retains independent client-side state for each active clip.
  - The existing backend stop remains global and drains every tracked `pw-cat` child. The per-tab policy chooses when the consumer requests that global stop; it does not add process, hardware, or per-clip-stop architecture.
- Constraints: the fire-and-forget playback API and client-side duration timer remain unchanged. Clicking any playing tile still invokes the global stop command, so stopping one tile in overlap mode stops all tracked soundboard legs; independent per-clip stop remains future work.
- Rationale: the UI already owns active playback state and is the real public consumer of the #399/#409 stop/play commands, so this keeps the change at that boundary. A `true` default is grounded in the actual frozen main behavior and makes old serialized boards stable while allowing an explicit per-tab opt-in to overlap.
